# Capacitor Mobile Wrapper — Audit Report

**Scope:** `apps/web` (the authenticated product app, `app.urganize.app`). This is a read-only audit — no code was changed to produce it.

**Date:** 2026-07-21

---

## 1. Monorepo structure

```
urganize/
├── apps/
│   ├── homepage/      # Marketing site (urganize.app) — Neon/Prisma, Tailwind v4
│   └── web/            # Product app (app.urganize.app) — Supabase, Tailwind v3 — THE app to wrap
├── packages/
│   ├── ui/             # Shared React primitives
│   ├── config/         # Shared tsconfig, ESLint, Tailwind preset
│   ├── pricing/        # Plan tiers/prices, shared by homepage + web
│   ├── lib/            # Stub
│   └── db/             # Stub
├── supabase/migrations/
├── turbo.json, pnpm-workspace.yaml, tsconfig.json, vercel.json
```

There is exactly one app that matters for a mobile wrapper: **`apps/web`**. `apps/homepage` is the marketing/waitlist site and has no bearing on a mobile shell — a "download the app" link on the marketing site is the only place it will ever need to know a mobile app exists.

**Recommendation: (a) new package inside this monorepo.** Nothing here argues for a separate repo:

- The Capacitor shell is not really "code" in the app-logic sense — it's a native project (`ios/`, `android/` folders generated by the Capacitor CLI) plus a thin config file (`capacitor.config.ts`) pointing at a URL. It has no shared business logic with `apps/web` beyond that URL and a few build-time constants.
- pnpm workspaces + Turborepo already exist to host exactly this kind of "another app, different build pipeline" addition — that's what `apps/homepage` already is relative to `apps/web`.
- Keeping it in-repo means the Capacitor config, app icons/splash screens, and any native-shell-specific docs stay versioned alongside the web app whose URL they point at, and a single PR can bump both if the pointed-at URL or bundle id ever changes.
- A separate repo would only make sense if the mobile shell needed its own CI/release cadence radically decoupled from `apps/web` (e.g. a different team, different review process, App Store review lag meaning native-shell changes ship far less often than web changes) — but the "remote URL" strategy (below) means the native shell itself changes *rarely* (only for icon/splash/native-plugin changes), while the actual product code inside the webview redeploys continuously via the existing Vercel pipeline. That asymmetry doesn't require repo separation, just infrequent native-shell PRs.

Proposed placement: `apps/mobile/` (Capacitor project + `capacitor.config.ts`), added to `pnpm-workspace.yaml` and given its own (mostly no-op for Turborepo purposes) entry — it has no `build`/`dev`/`lint` tasks that resemble the Next.js apps', so it may not need to participate in the Turborepo pipeline at all beyond living in the workspace for tooling consistency.

**Implemented as of this PR:** `apps/mobile/` exists exactly as proposed above.

## 2. Rendering mode: static export vs. remote URL

**Verdict: use the "remote URL" Capacitor strategy — point the wrapper at `https://app.urganize.app`.** A static export (`output: 'export'`) is not viable, and not close to viable.

What blocks it:

- **48 API route handlers** under `apps/web/app/api/**/route.ts` form the entire backend: auth-gated CRUD (releases, tasks, task-groups, comments, attachments, collaborators, workspace members, content-calendars/posts, notifications), Supabase Storage signed-URL upload flows, the two AI features and Chappi's agent loop, and Paystack billing (webhook, verify, start-checkout, promo redeem). A cron route (`api/cron/due-date-notifications`) is invoked by Vercel Cron with a `CRON_SECRET` bearer check. None of this can become static — webhooks, HMAC verification, and server-held Supabase admin credentials all require a live server process, full stop.
- One dynamic route, `apps/web/app/release/[id]/page.tsx`, does a request-time `redirect()` with no `generateStaticParams` — incompatible with export as written.
- `next/image` is used (`WorkspaceLogoSection.tsx`, `WorkspaceReleaseCard.tsx`) against Supabase Storage signed URLs, and `images.unoptimized` is not set — another export blocker on its own, though a minor one next to the API routes.
- No Server Actions and no `middleware.ts` exist (confirmed absent) — those aren't blockers here, but their absence doesn't change the API-route verdict above.

Given that, "bundle the web assets" is off the table without splitting the API layer into a separately-hosted backend — a large, unjustified architecture change for a v1-stage product with 1 paying user. The remote-URL strategy is the only sane fit:

- `capacitor.config.ts` sets `server.url = "https://app.urganize.app"` (and `server.cleartext = false`).
- **Implication: the app requires network connectivity to do anything** — there is no offline shell. That's consistent with the product today anyway (every page already round-trips to Supabase on load).
- **Implication: updates to web app code ship instantly, with no store review**, since the wrapper is just a window onto the existing continuously-deployed Vercel production. Only native-shell changes (icons, splash screen, added native plugins, permission strings) go through App Store / Play Store review.
- The existing `pnpm --filter @urganize/web build` / Vercel pipeline needs **zero changes** for this strategy to work — the mobile shell is a consumer of the already-deployed production URL, not a new build target of the Next.js app.

**Implemented as of this PR:** `apps/mobile/capacitor.config.ts` sets `server.url` to `https://app.urganize.app` with `allowNavigation` scoped to `*.urganize.app` domains only.

## 3. Auth flow

Supabase auth is simpler here than the "cookies vs. localStorage" framing usually implies: **there are no cookies at all.** The app uses `@supabase/supabase-js`'s plain `createClient()` (`apps/web/lib/supabase/client.ts`), configured with `persistSession: true` and no custom `storage` option — so it defaults to `window.localStorage`. Route protection is per-route (`getAuthenticatedUser` reading an `Authorization: Bearer` header), not middleware-based, which is exactly why no `middleware.ts` exists.

- **Zustand auth store** (`lib/auth-store.ts`) persists a *separate* localStorage key (`urganize-auth`, via Zustand's `persist`) purely to avoid a flash-of-unauthenticated-UI on load; it reconciles against `supabase.auth.getUser()`/`onAuthStateChange` afterward. It also writes a couple of plain localStorage keys directly (`urganize.last_auth_email`, a reauth timestamp).
- **Email/password:** direct `signInWithPassword`/`signUp` calls — no redirect involved, nothing webview-sensitive.
- **Password reset:** `resetPasswordForEmail(email, { redirectTo: `${window.location.origin}/auth/reset-password` })`, landing on `apps/web/app/auth/reset-password/page.tsx`.
- **Google OAuth:** `signInWithOAuth({ provider: 'google', options: { redirectTo } })` where `redirectTo` is built from `window.location.origin` + `/auth/callback`. A dedicated `apps/web/app/auth/callback/page.tsx` handles both the PKCE `?code=` exchange and the implicit hash-token flow, then redirects to `next` or `HOME_PATH`.
- **Invite accept flow** (`apps/web/app/invite/accept/page.tsx`) stashes an invite token in `sessionStorage` before kicking off the same Google OAuth redirect, then resumes after `/auth/callback` redirects back.
- No magic-link / passwordless flow exists.

**What breaks in a Capacitor webview, and what to change:**

1. **Cookies are a non-issue** — there are none, so there's no cross-scheme `SameSite`/`Secure` problem to solve. `localStorage` for a real `https://app.urganize.app` origin persists normally inside WKWebView/Android WebView, same as a desktop browser tab. This is good news; it's the reason the remote-URL strategy is low-risk on the auth-storage front specifically.
2. **`window.location.origin`-based redirect URLs need no code change** — they'll correctly resolve to the real `https://app.urganize.app` origin as long as the webview loads that URL (not a custom `capacitor://` scheme). The **Supabase Dashboard → Auth → URL Configuration redirect allowlist** needs the same URLs it already has for the web app to keep working (`/auth/callback`, `/auth/reset-password`, `/invite/accept?token=...`) — likely no *new* entries needed if the wrapper loads the same production origin, but confirm the allowlist doesn't have an origin-restriction that would reject requests originating from a webview user agent.
3. **The real required change is the Google OAuth redirect itself.** `signInWithOAuth` does a full-page redirect to Google's consent screen. Google actively blocks OAuth flows inside embedded/non-system webviews it detects by user agent (this is a long-standing Google policy, not Supabase-specific) — a bare Capacitor WKWebView will likely get rejected or blocked outright. The fix is to open the OAuth URL in the **system browser** via `@capacitor/browser` (SFSafariViewController on iOS / Chrome Custom Tabs on Android) instead of navigating the in-app webview, and register a **custom URL scheme or Universal/App Link** (e.g. `urganize://auth/callback` or an associated-domain App Link) so control returns to the native app after Google's redirect lands back on `https://app.urganize.app/auth/callback`. This is genuinely new work — nothing in the codebase does this today (confirmed zero `Capacitor`/platform-detection references anywhere in `apps/web`).
4. `sessionStorage` in the invite-accept flow is worth a second look once `@capacitor/browser` is introduced for OAuth — if the system browser is a genuinely separate storage context from the webview (behavior varies slightly by platform/plugin config), the stashed invite token may not survive the round trip. Verify empirically once the OAuth deep-link plumbing is built; don't assume it "just works" the way it does today in a single-webview browser tab.

**Implemented as of this PR:** on native platforms, `loginWithGoogle` (`apps/web/lib/auth-store.ts`) sets `skipBrowserRedirect: true` and a `redirectTo` of `com.urganize.app://auth/callback`, then opens the returned authorize URL via `@capacitor/browser`. `apps/web/components/providers/CapacitorAuthBridge.tsx` listens for the native `appUrlOpen` event and rewrites the scheme URL back into a same-origin `/auth/callback` path, reusing the existing callback page's PKCE/hash-token exchange rather than reimplementing it. The scheme is registered in both native projects (`apps/mobile/ios/App/App/Info.plist`, `apps/mobile/android/app/src/main/AndroidManifest.xml`). Manual dashboard steps (Supabase redirect allowlist, verifying the Google OAuth client needs no change) are in `docs/mobile/auth-setup.md`.

## 4. Billing surfaces (Apple IAP policy exclusion list)

Apple prohibits linking out to external payment for digital subscriptions from within a reviewed iOS app. Everything below needs to be hidden or made "web-only" in the iOS build:

| Surface | File | What it does |
|---|---|---|
| Paywall picker | `apps/web/app/locked/LockedPageClient.tsx` | Plan cards (Annual/Monthly/Label), currency toggle, **"Subscribe" button** → `POST /api/billing/start-checkout` → `window.location.href` redirect to Paystack's hosted checkout page |
| Post-checkout landing | `apps/web/app/payment/callback/page.tsx` | Polls `GET /api/payments/verify`, shows success/failure, routes to `/dashboard` |
| Checkout trigger route | `apps/web/app/api/billing/start-checkout/route.ts` | Server-side Paystack transaction init — the one call site is `LockedPageClient` above |

There is **no dedicated Settings → Subscription UI** — none of the Settings components (`Profile`, `Appearance`, `Security`, `WorkspaceArtist`, `WorkspaceLogo`, `Teammates`, `Releases`, `Session`, `DeleteAccount`) reference billing at all. The CLAUDE.md description of a "Subscription" surface in Settings refers to `/locked` itself, not a Settings panel — nothing extra to find there.

**Not a problem:** the **28-day no-card trial** (`POST /api/trial/start`, also triggered from `LockedPageClient`) and **promo code redemption** (`apps/web/app/redeem/RedeemPageClient.tsx` → `POST /api/promo/redeem`) touch no payment provider at all — these can likely stay visible in the iOS build with no Apple-policy conflict, since they don't sell anything.

The webhook (`api/webhooks/paystack`) and verify (`api/payments/verify`) routes are pure backend handlers with no rendering — no mobile-specific handling needed for them.

**No platform-detection mechanism exists today** (confirmed zero matches for `Capacitor`, `navigator.userAgent` app-detection, `isNativeApp` anywhere in `apps/web`) — this has to be built.

**Recommended mechanism:** detect the native wrapper via `Capacitor.isNativePlatform()` (from `@capacitor/core`, available client-side with no native plugin needed) at the top of `LockedPageClient` and `payment/callback/page.tsx`:
- On `Capacitor.getPlatform() === 'ios'`: hide the Subscribe button and plan-card pricing entirely; show only the trial CTA, promo redemption, and a plain-text "Manage your subscription at app.urganize.app" (or open that URL in the system browser via `@capacitor/browser`) — Apple explicitly permits *reading* subscription status and directing users to manage billing on the web, just not initiating purchase or linking directly to an external checkout from inside the app.
- Android has no equivalent Apple-style restriction for external payment links (Google Play's policy is narrower and mostly about Google Play Billing for certain content categories) — Paystack checkout can likely stay as-is on Android, opened via `@capacitor/browser` rather than the in-app webview, pending a policy read specific to the app's content category.
- This is the cleanest option among the three named in the brief (platform detection vs. hiding billing UI vs. always-external-browser) because it's additive to existing code — one conditional branch in one already-small page component, no restructuring of the checkout flow itself.

**Implemented as of this PR:** `apps/web/lib/platform.ts` provides `isIOSApp()`/`isNativePlatform()`. `LockedPageClient.tsx` hides the currency toggle, plan cards, and Subscribe button on iOS native (post-mount, to avoid an SSR/hydration mismatch), replacing them with a "manage on the web" message opened via `@capacitor/browser`; the trial CTA and promo-code link render unconditionally. On Android native, `handleSubscribe` opens the Paystack authorization URL via `@capacitor/browser` instead of `window.location.href`.

## 6. Environment, deploy, Zuplo, PostHog

- **Env vars** need no mobile-specific changes. `apps/web/.env.example` and the `turbo.json` allowlist already cleanly separate `NEXT_PUBLIC_*` (client-exposed) from server-only vars, and in the remote-URL strategy the native shell itself carries virtually no env vars of its own — it's just a webview pointed at a URL. All existing env-dependent behavior stays exactly where it is today, inside Vercel.
- **Deploys** are unaffected: `vercel.json` (root + `apps/web`) is unchanged by this work, auto-deploy on push to `main` via `turbo-ignore` continues exactly as today. The mobile shell is a *consumer* of the deployed URL, not a new Vercel build target. Verified: `pnpm --filter @urganize/web lint` (0 errors) and `pnpm --filter @urganize/web build` both pass unchanged after this PR's `apps/web` edits.
- **Zuplo AI gateway** (`lib/ai/provider.ts`) and **Chappi's transport** (`lib/chappi/runner.ts`, `@anthropic-ai/sdk`) are both confirmed pure server-side — no client exposure, no mobile implications whatsoever.
- **PostHog** (`instrumentation-client.ts` → `lib/analytics/client.ts`) has `autocapture: true` and session recording enabled by default (`maskAllInputs: false`, some masked attributes). Inside a webview, autocapture/pageview tracking will always show same-origin navigation with no real external referrer, and session recording adds capture overhead worth reconsidering for the wrapped context. **Worth a follow-up decision, not done in this PR:** either accept this as-is, or have the client detect `Capacitor.isNativePlatform()` and set a PostHog property (`app_context: 'ios_wrapper' | 'android_wrapper' | 'web'`) so mobile-wrapper sessions are distinguishable in dashboards, and optionally sample down or disable session recording for wrapped sessions.
- **No Edge Middleware / Edge Runtime** exists anywhere to interact oddly with webview networking — consistent with the "no middleware.ts" finding elsewhere in this report.
- **`apps/web/app/layout.tsx` has no `viewport` export and no `theme-color` meta tag at all today.** This is the one concrete gap the native shell will need the web app to close: add a `viewport` export (`viewport-fit: cover`) and `theme-color` so the status bar / safe-area behavior coordinates with whatever native chrome Capacitor adds (status bar color, notch handling). This is a small, low-risk `apps/web` change, not a mobile-repo-only concern. **Implemented as of this PR.**

## DECISIONS

1. **Monorepo vs. separate repo:** Monorepo. Add `apps/mobile/` as a new Capacitor project inside this repo, registered in `pnpm-workspace.yaml`. Nothing here justifies the coordination overhead of a separate repo — the mobile shell has no shared business logic beyond a URL, and the remote-URL strategy means native-shell PRs will be infrequent, not a release-cadence mismatch with `apps/web`. **Done.**

2. **Static export vs. remote URL:** Remote URL. `output: 'export'` is not viable — 48 API routes (auth, billing webhooks, AI, file uploads, cron) form the entire backend and cannot move client-side, plus one un-generated dynamic route and unconfigured `next/image` optimization. `capacitor.config.ts` should point at `https://app.urganize.app`. Trade-off to accept explicitly: the app requires network connectivity (no offline shell, consistent with today's product), and in exchange every web-code update ships instantly to installed apps with no store review — only native-shell changes (icons, splash, permissions, added plugins) go through App Store/Play Store review. **Done.**

3. **Auth changes required:** No cookie/SameSite work needed (Supabase auth here is 100% localStorage-based, no cookies exist). Confirm the Supabase redirect URL allowlist covers `/auth/callback`, `/auth/reset-password`, `/invite/accept` for the production origin (likely already does). The one real required build: move Google OAuth off the in-app webview onto `@capacitor/browser` (system browser), plus a custom URL scheme or Universal/App Link so the redirect back to `/auth/callback` returns control to the native app — Google blocks OAuth inside embedded webviews by user-agent detection, so this isn't optional. **Done** — see `docs/mobile/auth-setup.md` for the remaining manual dashboard steps.

4. **Billing exclusion approach:** Platform-detect via `Capacitor.isNativePlatform()` (from `@capacitor/core`, no plugin needed) inside `apps/web/app/locked/LockedPageClient.tsx` and `apps/web/app/payment/callback/page.tsx`. On iOS, hide the Subscribe button and plan pricing, keep the trial CTA and promo redemption (neither touches a payment provider), and point users to manage billing at `app.urganize.app` in the system browser. Android likely doesn't need the same restriction but should still open Paystack checkout via `@capacitor/browser` rather than the in-app webview. **Done.**

5. **Top 5 webview risks in this codebase, ranked:**
   1. Asset/file download anchors (`AssetCategoryGroup.tsx`) — plain `target="_blank"` links to remote Supabase Storage URLs, no native-safe download path exists at all today. **Fixed** (routed through `@capacitor/browser`).
   2. Google OAuth full-page redirect (`signInWithOAuth` + `/auth/callback`) — will likely be blocked by Google's embedded-webview detection without the system-browser + deep-link fix. **Fixed.**
   3. Missing `viewport`/`theme-color` config in `app/layout.tsx` — status bar and safe-area behavior will look wrong without it, a fast, low-risk fix. **Fixed.**
   4. Unguarded localStorage/sessionStorage access in onboarding and auth flows specifically — no try/catch anywhere, and these are the highest-consequence paths if storage access ever throws in a restricted webview context. **Fixed** for the highest-consequence sites (see §5).
   5. Clipboard (`navigator.clipboard.writeText`, no fallback) on the invite-link and AI status-update Copy actions — moderate but easy to defer since it degrades to "copy silently doesn't work," not a crash. **No change needed** — already guarded on inspection.
