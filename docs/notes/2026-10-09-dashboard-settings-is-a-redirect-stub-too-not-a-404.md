# /dashboard/settings is a redirect stub too, not a 404 (2026-10-09, v1.92.6, no flag)

> Moved out of CLAUDE.md on 2026-10-22 (verbatim). "This file", "above", "below" and "the X section" in here refer to the old single CLAUDE.md: find the named section in docs/notes/README.md.

Found on the live app: `https://app.urganize.app/dashboard/settings?settings=<tab>` showed the Settings pop-up drawn over the 404 ("We could not find that page"), with the tab titled "Page not found | Urganize"; a direct load, a reload or a shared copy of that URL was the 404. **Cause:** there was no `app/dashboard/settings` route, and `canHostSettings` accepts any `/dashboard…` path, so opening Settings from that 404 kept the 404's pathname under the pop-up (and closing it left you on the 404). No code in the repo emits `/dashboard/settings` — it is the path people guess, because every other app page lives under `/dashboard` — so the fix is a route, not a link change. **No flag, no schema change.**

- **`app/dashboard/settings/page.tsx` renders the existing `/settings` stub** (`app/settings/SettingsRedirect.tsx`) with a `Settings` metadata title: one client-side `router.replace` to `/dashboard?settings=…`, so Back leaves rather than bouncing off the stub, closing the pop-up lands on `/dashboard`, and the route stays `○ Static` (the stub reads `window.location`, not `useSearchParams`). Auth is the same as `/settings`: there is no `middleware.ts`, and a signed-out visitor is bounced by `/dashboard`'s own guard after the hop.
- **One map for both stubs: `settingsStubTarget(search, hash)`** in `lib/settings-stub-target.ts` (its own file because it reads `SETTINGS_SEARCH_ENTRIES`, and `settings-search.ts` already imports `settings-nav.ts`). Order: the pop-up's own `?settings=<segment>&section=` is kept as is (unknown → menu, as on `/dashboard`); else the old `/settings` `?tab=` / `#anchor` links through `legacySettingsTarget`, unchanged; else a hash naming any section in the search index (`#delete-rollouts` → Security & account, scrolled there); else the menu (General on a wide screen). `/settings` gains the first and third rules too, so `/settings?settings=billing` now opens Billing instead of the menu.
- **Not changed:** any OTHER unknown `/dashboard/<x>?settings=…` still draws the pop-up over that 404 (`canHostSettings` cannot know a path 404s); nothing links to such a path.
- **Tests:** `lib/settings-stub-target.test.ts` (every segment kept, section kept, unknown/empty → menu, `?settings=` beats hash and `?tab=`, legacy links unchanged, every section id in the search index resolves to its own segment, always lands on `/dashboard?settings=`, plus source checks that the route exists, renders the shared stub with a Settings title, and that the stub follows `settingsStubTarget` with `router.replace`).
- **Not verified in a browser, with a real session, or by `next build`.** Preview pass: load `/dashboard/settings`, `/dashboard/settings?settings=notifications`, `/dashboard/settings?settings=security&section=delete-rollouts` and `/dashboard/settings#delete-rollouts` signed in (each should end on `/dashboard?settings=…` with Settings on that tab over the catalog and no "Page not found" title), close it (lands on `/dashboard`), press Back, and load one signed out (should reach `/auth`).
