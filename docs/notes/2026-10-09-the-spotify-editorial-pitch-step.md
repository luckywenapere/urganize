# The Spotify editorial pitch step (2026-10-09, live at merge)

> Moved out of CLAUDE.md on 2026-10-22 (verbatim). "This file", "above", "below" and "the X section" in here refer to the old single CLAUDE.md: find the named section in docs/notes/README.md.

First of three PRs from the "release savings" briefs (the other two, a check before distribution and a record of release spend, are separate). **No flag**: it is part of the plan. One migration, `20261009100000_pitch_reminder_notification_types.sql` (three `notification_type` values), **not applied anywhere yet**. Not a scope expansion: it is a new step in the release playbook, owned by the release spine.

**What it is.** Every playbook (`single_v0.3`, `ep_v0.1`, `album_v0.1`) now carries one `editorial_pitch` step ("Pitch to Spotify editorial"), due 28 days before release day and blocked by the distribution order step, which has to be done at least 35 days out. It replaces the old Spotify pitch steps (`w6_spotify_for_artists_pitch`, `w5_ep_editorial_pitch`, `w5_album_editorial_pitch`), which were planned before the distributor had delivered. The step id is the same in all three, so one constant (`EDITORIAL_PITCH_TASK_ID`) names it. Upload dates stay where they were (single -42, EP -35, album -49).

**Where the rules live.** `lib/editorial-pitch.ts` is pure (ids, day maths, the 7-day window, reminder tiers, the backfill decision, copy, the four pitch fields). `lib/editorial-pitch-server.ts` does the reads and writes. `lib/editorial-pitch-draft.ts` is the prompt and the answer parser for the draft.

### Things worth knowing before editing this

1. **"Skipped" is not a status.** Releasing without a pitch sets the task to `cancelled` and writes `metadata.editorial_pitch.skipped_at`. An unknown status reads back as `todo` in about ten places, while `cancelled` is already handled everywhere, so a new enum value would have broken silently.
2. **The 7-day line is `daysToRelease <= 7` in Lagos days.** At that point Spotify no longer takes a pitch, so the step stops being a task and becomes a choice: the closed-window banner offers "Move release date" (owner only, it opens `ReleaseDetailsSheet` and saves through `POST /schedule`, which re-dates every open activity) or "Release without a pitch".
3. **The blocker is enforced twice.** The checkbox goes through `getTaskCompletionBlocker`, which says "Order distribution first. Spotify can't see the release until then." when the open dependency is the order step; `PATCH /api/tasks/[id]` refuses `done` on the pitch task with a 409 and the same line. That route deliberately enforces nothing else about order, so this is the one task it guards.
4. **Older rollouts get the step once**, the first time somebody opens them (`POST /api/releases/[releaseId]/editorial-pitch`, called by the workspace). It is a POST because it writes. The claim is a conditional update on the release row's `updated_at`, so two tabs cannot both insert. Outcomes recorded once: added, converted (an open old pitch task is rewritten in place), already there, already done. Nothing is recorded, so a later date or plan still gets the step, when there is no release day, no plan, a test rollout, an archived one, or 7 days or fewer to go.
5. **Reminders are their own sender, not `createTaskNotification`.** That helper dedupes only against UNREAD notifications, so a reminder that had been read would be sent again every morning. The sweep (`runEditorialPitchReminderSweep`, a passenger on the 07:00 UTC cron, never throws) checks for a row of that exact type for the task, read or unread. The tiers are windows (15 to 28 days is the 28 reminder, 9 to 14 the 14, 8 the 8), so a missed cron day does not lose one. The copy counts down to the day the window closes, so the 28-day reminder says 21. The ordinary due and overdue sweep skips this task, or it would call it overdue for three weeks while it can still be sent.
6. **Draft my pitch is an embedded UrgAns action** (`release.draft_spotify_pitch`, one-shot, `team_write`). It runs through `runUrgansAction`, so it gets the Manager-and-up gate, the credit hold and settle and the usage log with no new metering code. It asks the model only for the fields that are empty, uses only facts the rollout already holds (credit ROLES, never names), clamps the description to 500 characters at a word, and the write re-reads the task and merges into what is empty NOW, so text typed while the model worked is kept. Solo sees the fields and no button: `GET /api/tasks/[id]/editorial-pitch` returns `canDraft`, because no client knows the owner's tier. `canDraft` is also false while embedded actions are off (`NEXT_PUBLIC_FEATURE_URGANS_ACTIONS` plus the planner flag).
7. **The brief's text is used as written**, including the two strings that say "release" where the app says rollout ("Release without a pitch", "Spotify can't see the release until then"). Those two are allowed by exact phrase in `lib/rollout-vocabulary.test.ts`, and the new files are on its guarded list.
8. **Everything the sweep and backfill do fails soft.** A missing migration or a database blip costs the pitch step, never the page it was opened from.

### Verified

The full vitest suite passes (about 130 new tests: the pure rules, the backfill and reminder sweep against an in-memory stand-in for Supabase, the draft prompt and parser, the action against a fake database and model, the blocker copy, and `lib/editorial-pitch-guard.test.ts`, which reads the routes, the cron and the due-date sweep to hold the wiring). `tsc --noEmit` shows only the 8 documented `confirmed-action.test.ts` errors. Lint matches the clean-tree findings file by file (the three pre-existing `react-hooks/refs` errors in `WorkspaceView.tsx` and the accepted `set-state-in-effect` warnings; the new panel has none). `next build` is green by exit code with the embedded-actions and planner flags both off and both on, with `/auth`, `/dashboard`, `/onboarding`, `/settings` and `/locked` still static. Route probes on `next start`: all three new pitch routes, and the action route, answer 401 unauthenticated. **Ten deliberate breaks, each caught by a named test** (the 7-day line made exclusive, a draft overwriting typed text, the backfill claim removed, the reminder dedupe ignoring read rows, a reminder window widened, the 409 turned into a 402, the cron sweep removed, the ordinary sweep no longer skipping the pitch, the blocker copy dropped, and the blocker counting the wrong status), each restored byte-identical. The migration was applied twice on a real Postgres engine (PGlite) against a stand-in enum: the three values add in order, re-applying is a no-op, and an unknown value is refused. The panel, the closed-window banner and the details sheet were looked at through a throwaway page with made-up data (deleted): the draft fills all four fields and the counter reads 133/500, Solo shows no draft button, the blocked and skipped lines render, the sheet opens prefilled with Save disabled until something changes, and nothing overflows at 375px.

**Not verified:** nothing has run against a real database, a real model or a real session. No older rollout has been backfilled for real, no reminder has been delivered, no pitch has been drafted by a real model, and the migration is unapplied. The credit estimate for Draft my pitch is the default "up to 25 credits" because no real run has been measured; set `EMBEDDED_ESTIMATE_CREDITS['release.draft_spotify_pitch']` once one has.

### Activation

1. Apply `20261009100000_pitch_reminder_notification_types.sql`. Until it is applied, a reminder cannot be recorded (the sweep logs once and stops), and nothing else is affected.
2. Merge. The step reaches new rollouts straight away, and older ones the first time they are opened.
3. Draft my pitch appears only where embedded actions are on (`NEXT_PUBLIC_FEATURE_URGANS_ACTIONS` plus the planner flag) and the owner's plan is Manager or above.
