# Release spend (2026-10-09, live at merge, no flag)

> Moved out of CLAUDE.md on 2026-10-22 (verbatim). "This file", "above", "below" and "the X section" in here refer to the old single CLAUDE.md: find the named section in docs/notes/README.md.

Third of three PRs from the "release savings" briefs (the Spotify editorial pitch step and the check before distribution are the two above). A manager logs what each rollout cost, so the saving can be measured in interviews. **No feature flag** (founder call, 2026-10-09; the plan's earlier `NEXT_PUBLIC_FEATURE_RELEASE_SPEND` was dropped), so it is live at merge as v1.91.0. One migration, `20261009120000_release_spend.sql` (two tables, two functions, select-only policies), **not applied anywhere until the founder applies it, and it must be applied BEFORE the merge**: the Spend scene, both crons and the Home card all read the new tables. Not a scope expansion: it hangs off the rollout (the release spine) and moves nothing off the out-of-scope list, since it records what the user typed and reads no bank or payment provider.

### What did not match the brief, and what was built instead

1. **"A distribution order adds its line automatically" cannot happen yet.** Distribute is a readiness list plus a hand-off to the partner's own sign-up; there is no order endpoint and nothing charged. The writer, `addUrganizeSpendLine`, is built and tested, and nothing calls it. When the partner API lands, the order route calls it once the order succeeds; its `dedupe_key` makes a retry add nothing.
2. **Credit use is the one automatic line that exists today.** Credits are charged per team, not per release; the only attribution to a release is `ai_usage_events` (`release_id`, `credits_charged`), whose migration is applied (found in place on 2026-10-09), so the sweep can read it. A daily step on the 07:00 UTC cron (`runSpendCreditsSweep`) adds up each rollout's credits per Lagos day for the last 3 days and upserts one `Urganize` line per rollout per day at 15 naira a credit (`CREDIT_VALUE_KOBO`, in `lib/credits/pricing.ts`, because that module owns the naira rates). It refuses a partial read (a capped or failed page) so a low total never overwrites a right one, and does nothing while the usage table is missing.
3. **Category and source are text with CHECK constraints, not Postgres enums**, like every newer table here: an enum value needs a migration outside a transaction.
4. **Columns added to the brief's schema:** `workspace_id` in place of `team_id`; `dedupe_key` (a plain unique index, not partial, so an upsert can target it); `created_by` nullable for system lines; `asked_at` on `release_payback`, because the row is inserted when the question is sent and that is what makes it fire once.

### Things worth knowing before editing this

1. **Who can see spend is ONE SQL function.** `can_view_release_spend(release_id, user_id)` is true for the release owner and for an active owner or admin member of the owner's team who is not limited to another artist. RLS uses it with `auth.uid()`, the routes call it as an RPC, and it refuses to answer for anybody but the caller, so a signed-in person cannot probe someone else's access. Every route FAILS CLOSED: a null answer is a 500, never "visible". Both tables have select policies only; every write is a service-role route.
2. **Money is whole kobo.** `lib/money.ts` holds `formatNaira`, `nairaToKobo` and `koboToPlainNaira` (moved out of `lib/pitch-payments.ts`, which re-exports them); the form takes naira text and the server parses it, so no floating-point money reaches the database. The limit is 1,000,000,000 naira a line, mirrored by a CHECK.
3. **Automatic lines cannot be changed.** A line with source `urganize` answers 403 to edit and delete, and the update and delete queries ALSO carry `.eq('source','manual')`, so the refusal does not rest on one check. The screen shows the "Ordered in Urganize" tag and no buttons on those lines.
4. **Spend routes answer 403, never 402.** The fetch interceptor redirects the browser to `/locked` on any same-origin 402; a team behind the wall must not be thrown out of the app by looking at its own spending. A guard test pins it.
5. **The spreadsheet is built to open cleanly in Excel and Sheets.** UTF-8 byte-order mark, raw naira numbers (not "₦7,000") so a column can be summed, and any cell that begins with `=`, `+`, `-`, `@` or a tab is prefixed so a pasted formula cannot run. It goes through `shareOrDownloadTextFile` so the native shell gets the share sheet, and it is not offered while the list is empty.
6. **Payback is asked once.** Day 30 after release day (Lagos) is the target, with a 3-day catch-up window so a missed cron day does not lose it and history is never mass-asked. The sweep inserts the `release_payback` row with ignore-duplicates BEFORE notifying, and notifies only when the insert actually created a row; a second run inserts nothing and sends nothing. The push and the email (`release_payback_question`, reminders category, founder-note register) carry the brief's question and link to `?release=<id>&scene=spend`. Test rollouts and archived ones are skipped.
7. **The Home card is for managers.** The server adds up only the rollouts this person may see (`release_spend_by_category(user, since)` applies the same visibility function), so anybody else gets nothing and no card. It shows only when there is spend in the last 90 days, and a failed read draws nothing, because Home never shows a broken card. It reuses a `BarList` extracted from the admin Metrics page.
8. **The scene is never cached, on screen or on disk.** It is money, and a person's right to see it can change, so every open asks again. The menu row appears only after a probe says the viewer may see spend (`stores/useSpendAccessStore.ts`, cleared on sign-out), and the Spend section is keyed on the rollout so one rollout's total can never show under another.
9. **No "you saved ₦X" number anywhere.** The brief says so and a guard test scans the new files for it.
