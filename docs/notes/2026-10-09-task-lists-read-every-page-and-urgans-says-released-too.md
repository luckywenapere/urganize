# Task lists read every page, and UrgAns says "released" too (2026-10-09, v1.92.9, no flag)

> Moved out of CLAUDE.md on 2026-10-22 (verbatim). "This file", "above", "below" and "the X section" in here refer to the old single CLAUDE.md: find the named section in docs/notes/README.md.

Two fixes found by reading what the live app counts. **No flag, no schema change.**

1. **Task lists stopped at 1,000 rows.** `TaskService.getTasksForUser` and `getWorkspaceTasks` used one `.limit(1000)` and only logged when it was hit. A team with 16 rollouts of about 64 activities holds roughly 1,024, and the list is ordered by date, so the LATEST-dated activities silently vanished. Everything that counts activities per rollout read a smaller number: the Catalogue's progress, `isRecapEligible`'s "every activity is done" (so `displayStatus` could read "Released" late or not at all), Home and the assistant's snapshot. The command centre loads the whole workspace, so any big team hit it on every visit.
   - **`lib/paged-rows.ts`**: `readAllPages(fetchPage)` reads pages of `ROWS_PAGE_SIZE` (1,000, which is also Supabase's own `max_rows`) up to `ROWS_MAX_PAGES` (5, so 5,000 rows) and returns `{ rows, truncated }`. A second page is asked for only when the first came back exactly full, so a team under 1,000 pays nothing extra. A failed page THROWS rather than returning a short list that looks complete. `inChunks` splits id lists.
   - **`id` is the last sort key** on both reads. `due_date` and `position` are not unique, and a tie on a page boundary would otherwise skip or repeat a row. `lib/paged-rows.test.ts` fails if either `.order('id'...)` goes.
   - **The ceiling is still named (`TASK_LIST_MAX_ROWS = ROWS_PAGE_SIZE * ROWS_MAX_PAGES`) and still logged when hit.** A silent cap would read as "that's all there is."
   - **`loadTaskCounts` (comment and file counts) now asks in chunks of 150 ids.** One `.in('task_id', ids)` with 1,000 uuids is a URL of about 38 KB, past what the gateway accepts, and the function swallows errors, so a refused request read as "no comments or files" for every activity. Chunks run in parallel and a failed chunk only drops its own counts.
2. **UrgAns reported the raw stored status.** Nothing writes `released`, so the assistant told people a finished rollout was "draft" while the Catalogue showed Released. `lib/chappi/release-status.ts` (`assistantReleaseStatus`) is the Catalogue's `displayStatus` with the assistant's inputs: the workspace snapshot, `get_workspace_context`/`get_release_context`, `list_releases` (date alone, since it loads no activities), `get_release` and `compare_releases`. `lib/chappi/release-status.test.ts` scans those four sites so none can print the raw status again. Same derived rule as everywhere else (`lib/recap-eligibility.ts`), not a new definition.

**Verified:** new tests (16 for paging and chunking, 16 for the assistant status) pass; the paging tests fail with the second page removed (6 fail) and with the id tiebreak removed (1 fails), and the assistant tests fail with the snapshot wiring reverted. **Not verified against a real database:** no team over 1,000 activities has been read for real, and the chunked count lookups have not run against production. Worth one look on the team that triggered it: open the Catalogue and confirm the latest rollouts' progress counts now match their activity lists.
