# Work after the reply goes through after() (2026-10-09, v1.92.12, no flag)

> Moved out of CLAUDE.md on 2026-10-22 (verbatim). "This file", "above", "below" and "the X section" in here refer to the old single CLAUDE.md: find the named section in docs/notes/README.md.

Found by reading the server code for work started with a bare `void promise()` after the response was built. On a serverless host the function can be frozen once the reply is sent, so that work is cut off or waits for the next request on the same instance. That is how an assignment notification, the "who changed this" row, the founder's "a team just paid" alert or a billing event can quietly never happen. **No flag, no schema change.**

- **One helper, `lib/after-response.ts`:** `afterResponse(label, task)` hands the work to Next's `after()`, which keeps the invocation alive until it finishes without delaying the reply. A failure is logged with the label and never rethrown, because the thing being reported (the update, the payment) already succeeded. Outside a request scope `after()` throws synchronously, so it starts the work right away and does not wait on it (what the bare `void` did), which also keeps scripts and unit tests working.
- **Converted sites (each with a label):** task assignment and status notifications and the activity row in `POST /api/tasks` and `PATCH /api/tasks/[id]`, the editorial pitch skip record, the MCP tool-call record, `start-checkout`'s "checkout started" event, the Paystack webhook's three founder alerts (checkout completed, plan change swap owed, payment failed), the trial-started record in `ensureOwnedWorkspace`, both referral-tagged records, and the MCP token's last-used stamp. Values read from `body`, `workspace` and `row` are captured into consts first, so the callback does not depend on a later mutation.
- **`logTaskActivity` now warns on an insert error** instead of ignoring the result, so a missing table is visible.
- **The guard, `lib/after-response-guard.test.ts`,** reads the real sources: no bare `void` on the reporting helpers (`createTaskNotification`, `logTaskActivity`, `logBillingEvent`, `notifyFounder`, `touchLastUsed`), no `void (async` in any route, each converted site imports the helper and calls it with its label, and the helper uses `after(run)` inside a catching `run`. A new route that goes back to `void` fails here, not in production.
- **Not changed on purpose:** money-moving awaits stay awaited; calls that only report (analytics, records, alerts) are the ones that move. Server PostHog capture already flushes through `shutdownServerAnalytics`, and the notifications bell helpers already await.

**Verified:** `lib/after-response.test.ts` (inside and outside a request, logging, no rethrow, a synchronous throw from `after`) and the guard, 21 tests; five deliberate breaks each caught by a named test and restored byte-identical (the tasks route back to bare `void`, the helper not calling `after`, the helper no longer catching, the webhook's payment-failed alert reverted, the MCP token import removed). Full suite 7,652 passing, `tsc` clean, lint clean on every touched file, `next build` green with `/auth`, `/dashboard`, `/onboarding`, `/settings` and `/locked` still static.

**Not verified:** nothing has run on a real serverless deployment, so that `after()` actually keeps a Vercel invocation alive through a slow push, and that the three founder alerts still arrive after a real webhook, rests on Next's documented behaviour and the unit tests. Worth one look after deploy: assign an activity to a teammate and confirm their notification and the `task_activity` row both appear, and check the founder alert after the next real payment.
