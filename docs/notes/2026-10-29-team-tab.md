# The Team tab and chosen-rollout access (2026-10-29, #853, no flag)

Founder asked for a Team tab after Artists (Deel-style), and for Relationships to be parked. Mocks approved in three rounds: `docs/mocks/team-tab/mock.html` (light mode, desktop card grid with centred cards, phone list).

## What it is

- **Nav.** A `team` area right after Artists in `lib/shell-nav.ts` (`TEAM_HREF = /dashboard/team`, one destination, no sub-tabs). On a phone it is in the More sheet. Solo artists get it tucked under More (`lib/role-views.ts`, feature `team`). In search (`lib/app-pages.ts`) the team words moved from Settings to Team.
- **Relationships is parked.** The whole Relationships area (Directory and My People) is in the nav only when My People is unpaused (`flags.relationships`, see `lib/paused-features.ts`). The Directory page still opens from search and its links.
- **Settings → Team is gone.** `visibleSettingsSegments` has `team: false`. The segment key stays so old links resolve: `settingsDeepLink({segment:'team'})`, `useOpenSettings({segment:'team'})` and a typed `?settings=team` (SettingsModalGate) all go to `/dashboard/team`. `HOME_TEAM_HREF` points there too.
- **The page** (`app/dashboard/team/TeamPageClient.tsx`): People and Settings segments. People: centred cards on a computer (online dot, role, last active, Open / Late / Done 7d, next task, an "Invite someone" card while seats are left, dashed cards for waiting invites), a list on a phone. A person opens in `TeamSheet` (right drawer on a computer, sheet on a phone) with their open tasks grouped Late / This week / Later, each linking to its rollout. Settings: team name (managers), seats, invite links (the existing `TeamLoginsSection`), Leave (anyone but the owner).
- **"workspace" never shows in copy** (house rule, `house-copy-ratchet`): the UI says "team". Code and tables keep workspace names.

## Who can do what

- Everyone on the team reads `GET /api/team` (`lib/team-page-server.ts`).
- Managers = workspace role `owner` or `admin` (`canManageTeam`), the same rule the members API uses. They get Invite, Remove, Change role or access, and Rename (`PATCH /api/team`).
- Anyone but the owner can leave (`POST /api/team/leave`, an open route so a lapsed team can still be left).
- **Hand over is not built** (#856): rollouts are keyed to the owner's user id (`releases.owner_user_id`), billing to the owner's subscription, and `workspaces.owner_id` is unique while every user already owns a workspace. Swapping `owner_id` would hide every rollout from the team and change the plan.

## Chosen-rollout access

- Column `workspace_members.release_scope_ids uuid[]` (migration `20261029120000`, applied 2026-10-29, backup `workspace_members_backup_20261029`, 106 rows). NULL = no limit. **An empty array is a real limit: sees nothing.** Never widen it to everything the way a nulled `artist_scope_id` does.
- Loaded with the artist limit in `resolveWorkspaceAccessContext` into `releaseScopeByOwnerId` / `releaseScopeByWorkspaceId`.
- **The one check is `isReleaseInScope` in `lib/release-access.ts`.** `decideReleaseAccess` uses it, and so do `ReleaseService.getReleasesForUser`, `/api/releases`, the command center and the UrgAns activity. A rollout limit with no release id fails closed, so pass `releaseId` to `decideReleaseAccess`.
- **Task lists take the whole access context** (`TaskListScope`, required) and filter with `dropRowsOutsideScope`. This also fixed a real leak: `/api/tasks`, `/api/tasks/all` and the UrgAns task tools ignored the artist limit until now.
- Artist-wide things are hidden from a rollout-limited member: artist facts, records in the making, record asks on Home, press kits, contacts, opportunities.
- Release chat, handoff people and grants pushes respect the limit.
- Set at invite (`releaseIds` on `POST /api/workspace/members/invite`, kept only if the owner owns them) or later with `PATCH /api/team/members/[id] { role, access }`. Invite links stay "all" or "one artist".
- Managers always see everything. The artist role always means one artist.

## Leaving or removal

Open tasks (not done or cancelled) go back to the owner (`returnOpenTasksToOwner`). This applies to the existing `DELETE /api/workspace/members/[id]` too, and the UrgAns remove-teammate card says so.
