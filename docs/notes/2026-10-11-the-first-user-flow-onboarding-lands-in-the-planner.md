# The first-user flow: onboarding lands in the planner (2026-10-11, v1.105.0, founder-approved, no flag)

> Moved out of CLAUDE.md on 2026-10-22 (verbatim). "This file", "above", "below" and "the X section" in here refer to the old single CLAUDE.md: find the named section in docs/notes/README.md.

A browser test of a brand-new signup found eight problems between onboarding and the first plan; the founder approved every fix. No flag (the invite gate's live-by-default precedent), no migration.

1. **The planner no longer re-asks what onboarding asked.** `lib/planner-intake-steps.ts` (pure, tested) turns the prefill into a list of visible steps; `PlannerIntakeModal` walks that list for Continue, Back, the progress bar and "Question N of M". Rules: a prefilled type skips Q1 (unchanged); a prefilled **usable future** date (`isUsableFutureYmd`, real calendar day, today or later) skips Q2; a prefilled `artistName` skips the artist question. **Only an artist the caller vouches for skips it** (the scoped rollout's own artist via `scopedRolloutIntakePrefill`, or the one onboarding just typed), never the identity card or profile name on its own, because a team can have several artists and a note or chip has no rollout. Notes, chips and the create flows keep their old questions. A first plan from onboarding asks four: what is done, what matters most, budget, what to cover. `WorkspaceView.openPlanIntake` now passes `{releaseType, releaseDate, artistName}` from the scoped rollout.
2. **Onboarding step 4 (index 3) asks for the artist name**, required, max 120 (`MAX_ONBOARDING_ARTIST_NAME_LENGTH`, the same ceiling as every artist field). It is on the draft (`lib/onboarding-draft.ts`), sent as `artistName` on `POST /api/releases` (which stores it on the rollout and creates the team's artist when new), and passed to signup metadata for every role (the profile's `artist_name` is still only written for an `artist` account, as before). The account step's own artist field is gone; an `artist` account reads the draft's.
3. **Every onboarding exit lands on `/dashboard?release=<new id>`** (`onboardingLandingPath`, via `resolvePostSignupDestination`'s `homePath`, so card trial, claim, welcome and pitch intents still win) and, when the create answered `plannerPending`, opens the planner there with `source: 'onboarding'`. The hand-off is a per-tab sessionStorage marker (`markOnboardingPlannerHandoff` / `takeOnboardingPlannerHandoff`, 60 minute TTL) that WorkspaceView takes only once that exact rollout is in the catalog with no activities.
   - **The first session stays quiet** (`lib/first-session.ts`). At the end of onboarding one localStorage record is written (rollout id, time, a tab id that also goes in sessionStorage). "First session" = same tab id and under 12 hours. While it holds: no install card (`InstallAppPrompt` neither arms nor fires, nothing is spent), no catalog tour (not marked seen, so it starts next visit), no rollout tour offer after the build, and the share sheet's pending onboarding offer is dropped. **Deliberate widening of the brief:** the brief said "until the first plan is built and the invite gate is cleared"; the quiet lasts the whole first session instead, so nothing pops up between the plan landing and the gate, or straight after the gate. The rollout tour offer is therefore never offered to an onboarded user (it only fires at build time); the HelpMenu replay still reaches it.
   - **"Tell people it's coming" moves to Home on the next visit** (founder call). Onboarding no longer calls `markPendingFirstShare`; the record keeps `shareReleaseId` (only when the server said `firstRelease` and share is on), and `useDeferredFirstShareOffer` in `ShareSheet` opens it once on `/dashboard/home` in a LATER session (new tab, or the 12 hours are up), within 14 days, through the same quiet-moment checks and once-per-person record as the old offer. Sign-out clears the record.
4. **Step 6 ("Create account & rollout") no longer looks frozen.** The progress line is staged (`lib/onboarding-progress.ts`: "Creating your account…" → "Setting up “<title>”…" → "Almost there…" after 8 s) with "This takes under a minute." under it, a ref guards a double submit, and `beforeunload` asks before leaving while it runs. Speed: the chain is signup → (legacy trial) → `POST /api/releases`, which cannot be parallelised across steps, so the trims are inside the create route: the six schema probes in `ensureReleaseOpsSchema` run together (errors still reported in order), the release count runs beside them, the metadata row and the created event are written together, and the activation check and the reminder queue moved to `afterResponse`. `finishToDashboard` sends the onboarding PATCH and the referral report together. **Not profiled against production**: where the 45 to 60 seconds actually went (cold starts, the region hop to Supabase, the PostHog flush in the route's `finally`) was not measured, so how much this saves is unknown. If it is still slow, time each request in the browser's network tab first; the PostHog `shutdown()` in the create route's `finally` is the next suspect.
5. **The last question is "What should the plan cover?"** with every scope ticked. The data model did not change: `exclusions` is still the scopes to leave out, now the UNticked ones (`coveredScopes` / `toggleCoveredScope`).
6. **A team's first plan is free.** `lib/credits/first-plan.ts` is the rule, `first-plan-server.ts` reads the facts (approved `release_plan_drafts` rows for the team owner, and the owner's rollouts with `metadata.planned_by_urgans`). Both planner doors (`runUrgansAction` for `release.draft_plan`, and `POST /api/releases/[id]/plan`) skip the hold and the charge when it is free, so a short balance cannot refuse it either. Fails toward charging on an unreadable count. Known and accepted: deleting every planned rollout makes the next plan "first" again. The intake footer asks `/api/urgans/usage?firstPlan=1` and says "Your first plan is free." instead of the cost line. After any build the modal calls `invalidateUrgansUsage()` so the header credits pill and strip re-read.
7. **Step 7's Skip says "Continuing…"**, Send says "Sending…" (`inviteStepButtonLabels`).
8. **InviteGate's "Continue to my plan" closes panels**: `inviteGateContinueUrl` strips `settings`, `section`, `scene`, `month`, `task` and `new` and replaces the URL. The gate itself is untouched; the planner opening on arrival does not trip it, because its scrolls are inside `[role="dialog"]` and a rollout with no activities is not gated.

**Tests:** `lib/planner-intake-steps.test.ts`, `lib/first-session.test.ts`, `lib/credits/first-plan.test.ts`, `lib/onboarding-draft.test.ts`, `lib/onboarding-progress.test.ts`, additions to `lib/invite-gate.test.ts` and `lib/onboarding-next-hint.test.ts`, and `lib/first-user-flow-guard.test.ts` (source checks for the wiring no component test can reach). **Not verified in a browser or with a real signup**: the four-question walk, the landing, the quiet first session and the next-visit share offer all rest on unit tests and the type-check. Worth one real signup after deploy.
