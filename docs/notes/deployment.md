A project with a working gate cannot do that, and a project without one cannot produce that cancel message.

That was true when he looked; something was installed on the marketing project in the two days between then and #579. The Deploy Configuration bullet at the end of this file and item 1 of *"A docs-only merge no longer costs four deployments"* both said the same and are corrected with it. **WHICH command is installed cannot be read from outside** — *"Canceled by Ignored Build Step"* is Vercel's generic message for any ignore command exiting 0, so it cannot tell bare `turbo-ignore @urganize/homepage` from `scripts/vercel-ignore-build.sh @urganize/homepage`. The test that distinguishes them is a markdown file INSIDE a package, and it is spelled out in item 6 of that section.

**Two claims below are now dated rather than current because of this:** the four-deployments-per-merge arithmetic in point (4), and point (9)'s measurement that a docs-only merge promotes both apps. Each carries its own note.

**CI/CD:** Vercel git integration only. No GitHub Actions. No automated tests. `pnpm lint` is the only CI gate.

**`vercel.json` lives at the REPO ROOT, and only there (found 2026-08-12).** Both Vercel projects have Root Directory `.`, so Vercel reads `/vercel.json` for both and **never reads `apps/*/vercel.json` at all**. Those per-app files look authoritative and are inert. This cost real delivery: the two cron jobs were declared in `apps/web/vercel.json`, so they were never registered with Vercel — the Cron Jobs tab sat on its empty-state tutorial while the hourly due-date sweep and the 15-minute notification flusher had simply never run. The engagement drip masked it, because that path also runs opportunistically from `POST /api/engagement/login-ping` on sign-in and so kept working without a cron. Consequences to keep in mind:
- **Cron paths must exist in `apps/web`, but they register on BOTH projects.** `the-urganization` also registers `/api/cron/*` and 404s them every hour, since those routes only exist in the product app. Accepted as harmless noise. The clean fix is setting the `urganize` project's Root Directory to `apps/web` so it reads that app's own file, but that changes how the monorepo install/build resolves and must be validated on a preview deploy before anyone tries it. If Root Directory ever does change, **the crons have to move with it** or they silently vanish again.
- **`apps/homepage/vercel.json` is inert too.** It sets `NEXT_PRIVATE_BUILD_WORKER=webpack` for the homepage build, and that has never taken effect. Left alone deliberately: hoisting it to the root would apply it to the product app's build as well.
- Crons register **on production deployment**, so a change to the block only takes effect after it merges to `main`.

**The Vercel account is on the HOBBY plan, which caps cron jobs at once per DAY (2026-08-12).** Any expression that would fire more often — `0 * * * *`, `*/15 * * * *` — **fails the deployment**, it does not degrade. Both schedules in this repo were exactly that, so even once they were moved to the file Vercel reads, the deploy failed until they were made daily. The two problems had been hiding each other: sitting in an unread file, the illegal schedules were never validated. Correcting an assumption recorded elsewhere in this file: two cron entries do **not** imply a paid plan.

Current schedules, both daily and both approximate — Hobby precision is ±59 minutes:
- `/api/cron/due-date-notifications` at `0 7 * * *` (≈08:00 WAT) — the deadline sweep plus the weekly motivational nudge.
- `/api/cron/notifications` at `0 8 * * *` (≈09:00 WAT) — the `scheduled_notifications` flusher.

**What daily costs, and what it does not.** The deadline tiers (7d/3d/1d) and the weekly nudge are unaffected in substance: both are day-granularity, and the nudge's gate is "has this user had one in the last 7 days", not a function of sweep frequency. What genuinely degrades is `momentum_30m`, the drip step meant to land 30 minutes after a login — a once-daily flusher cannot honour that. It partly survives because `POST /api/engagement/login-ping` also flushes opportunistically, so the step goes out on the user's *next* sign-in rather than 30 minutes into the current one. Restoring true 30-minute behaviour means Pro, not a code change.

**The same Hobby plan also rate-limits DEPLOYMENTS, and that bit on 2026-09-07.** Both Vercel projects began reporting a FAILING commit status reading *"Deployment rate limited — retry in 24 hours"*, which looks exactly like a broken build and is not one. Four things worth knowing before anyone debugs code over it. **(1) It lands on `main` too**, not just on open PRs — so a PR check failing this way is not a regression from that PR; compare against `main`'s own commit status before investigating anything. **(2) THE TWO PROJECTS EXHAUST INDEPENDENTLY, and the combined commit status hides it.** GitHub shows one red X if EITHER project fails, so a red check does NOT mean your app failed to deploy — read the per-context statuses (`gh api repos/OWNER/REPO/commits/SHA/status`) before concluding anything. Measured on 2026-09-07: `the-urganization` ran out first, so `813be523` (#531) shows `the-urganization: failure` alongside `urganize: success — Deployment has completed`, and the recap feature it carried went live normally. `urganize` ran out at the very next merge, `ae48c879` (#530), which is where the product app actually stopped shipping. **Corrected 2026-09-07 within the hour:** this bullet first named #531 as the first stranded commit, from reading the combined status rather than the per-project ones — the mistake the bullet now warns about, made while writing it. **(3) The trap is verification.** A session that ships a feature during the window and then "verifies it in production" is really testing the last successfully-deployed bundle, which invites the wrong conclusion that the change failed. **(4) Two projects double the cost of every push**, and docs-only changes are not exempt: a root-level edit such as this file fires a preview build on BOTH `the-urganization` and `urganize` (observed on #526 and #534), plus a production deploy per project on merge. `turbo-ignore` trims per-app builds but does not prevent this. **The arithmetic is exact rather than roughly: each merge costs FOUR deployments** — a preview on each of the two projects, then a production deploy on each — and Hobby caps deployments at 100 a day, so 25 merges is the ceiling and the "roughly 25" figure above is that number confirmed rather than estimated. **AMENDED 2026-09-11: four is now the CEILING rather than the flat rate**, because `the-urganization` gained an Ignored Build Step (see Hosting above). A merge that reaches only `apps/web` now costs two or three — #579 is the measured case, where the marketing project cancelled its preview — while a merge touching `packages/*`, the root, or both apps still costs four. Whether a CANCELLED deployment still counts against the 100 is **unknown and unread** (vercel.com is policy-blocked from the agent sandbox), so do not assume the ceiling moved with the rate; the check is one look at the project's deployment list after a skip. **(5) IT EXHAUSTS ACROSS SESSIONS, WHICH IS WHY IT LOOKS LIKE A BROKEN PUSH.** The budget belongs to the ACCOUNT, not to a session or a branch, so several Claude sessions merging independently drain it together and **none of them can see the others doing it** — each one's own pushes look fine until they suddenly stop landing. Measured on 2026-09-07: **40 merges to `main` in one day**, about 160 deployments against a cap of 100. That is the shape to recognise on any "my last few pushes did not go live, and not just in this chat" report. **(6) A SECOND EXHAUSTION THE SAME DAY WENT DIFFERENTLY, so do not expect the staggered pattern in (2).** That morning the two projects ran out one merge apart; that evening both went at the same instant, narrowed to a two-minute window — **#545 at 21:18 UTC reported "Deployment has completed" on BOTH projects, and #546 at 21:20 UTC reported rate limited on BOTH.** Read the statuses rather than assuming either pattern. **How to read them when `gh` is unavailable** (it is not installed in the Claude Code remote environment, and a direct `curl` to api.github.com is refused there by policy): the GitHub MCP server's `pull_request_read` with `method: 'get_status'` returns the combined status of a PR's head commit, per context, which is the same data the `gh api` line above names. It reads the PREVIEW build; production deploys are keyed to `main`'s own commits and cannot be reached that way, but the limit is shared so the preview timeline dates the exhaustion either way. **(7) SAVING AN ENV VAR CAN ITSELF BE THE DEPLOY, which is worth knowing precisely because a rate limit hides it.** The standing advice for a `NEXT_PUBLIC_*` flip — that it needs a commit which actually touches `apps/web` — describes the git path and is not the only one: saving the variable in the Vercel dashboard triggers its own redeploy (recorded on the EPK flip, 2026-08-14). On 2026-09-07 that is what actually delivered the metadata and capture flags: the founder's env-var save redeployed and landed before 21:18, while the v1.30.0 version-bump commit that was *supposed* to inline them merged at 21:30 and never deployed at all. Both scenes appeared in production regardless, which is exactly the trap in (3) read in reverse — a change that works for a reason other than the one you shipped. Recovery needs no re-merge — the next successful deploy ships the accumulated tip, or `main` can be redeployed from the dashboard once the window clears; **re-merging actively hurts, since each attempt burns four more deployments against an exhausted budget.** Merging past the failing check is safe for a docs change and is a judgement call for code, which will sit undeployed either way.

**Two more things about that limit, measured on 2026-09-08 while checking whether the tip had shipped.** **(8) RECOVERY IS FAST — tens of minutes, not the day the message threatens — and the two projects do not recover together.** Measured across three reads of the same evening: `#546` at **21:20:32Z** was refused on BOTH projects; `#551`'s head still showed `the-urganization: failure` at **21:37:34Z**; and the same head showed `urganize: success — Deployment has completed` at **22:00:40Z**. So `urganize` was building again about **forty minutes** after being refused, while the marketing project was still out at the seventeen-minute mark. By 2026-09-08 15:30Z both were accepting deploys again (both `pending — Vercel is deploying your app` on `#553`). **Corrected within the same change:** this paragraph first put that recovery at five and three-quarter hours, by anchoring to the MORNING exhaustion at ~16:19 rather than to the 21:20 refusal that actually preceded it — the same class of error as reading the combined status in (2), and caught only because `#552` recorded the 21:20 timestamp independently. **(9) A DOCS-ONLY PUSH CANNOT PROMOTE THE APP, so it is the wrong instinct for kicking a stalled deploy** — and it is worse than useless, since the re-merge warning above means it burns four deployments to change nothing. `turbo-ignore` answers *"This project and its dependencies are not affected / Ignoring the change"* when no app changed, so Vercel records a SKIPPED deployment and the previous build stays live. Promoting `apps/web` needs a commit that touches `apps/web` — a version bump is the conventional way, since `apps/web/package.json` is part of that package. Verified both directions on 2026-09-08: a root-only edit is ignored, and `0cabd27` (five `apps/web` files) answers *"This commit affects @urganize/web / Proceeding with deployment"*. **CORRECTED 2026-09-08, LATER THE SAME DAY, AND THE HEADLINE CLAIM IS WRONG: A DOCS-ONLY MERGE DOES PROMOTE THE APP.** Measured through the version endpoint the moment it went live: `#557` and `#558` touched **zero** files under `apps/web` or `apps/homepage`, and `curl /api/version` on BOTH hosts then reported `28725f8` — `#558`'s own squash. That sha is read from `VERCEL_GIT_COMMIT_SHA`, which is baked per deployment, so a build genuinely ran and was promoted for a commit that changed only this file. **AMENDED 2026-09-11, and read this before repeating the measurement: that reading is dated, because BOTH hosts reporting the docs-only sha was measured while neither project had an Ignored Build Step.** `the-urganization` has one now (see Hosting above), so a docs-only merge today should skip the homepage and still promote `apps/web` — expect the two hosts to DISAGREE, with `urganize` on the new sha and the marketing site on an older one. That is the gate working, not a stranded deploy, and `/api/version` on both hosts is how to tell the two apart. **What is still true is the half about the TOOL**, re-confirmed the same hour: `turbo-ignore @urganize/web` answers "not affected / Ignoring the change" for that tip both with an explicit `--fallback` and with its own `HEAD^` default, so it is not failing open. What was never actually tested is the PIPELINE — the bullet ran the tool and generalised, which is the same shape of error as reading a combined status in (2). The likeliest explanation is that the Ignored Build Step is not gating these builds as the Deploy Configuration section claims, and **that can only be settled in the Vercel dashboard** (is the field populated on both projects, and what do the build logs say) — so treat the mechanism as open and the OBSERVATION as settled. Two practical consequences: **there is no such thing as a cheap docs merge** (which is what (4)'s four-deployments-per-merge arithmetic already implies, from observation, and (9) contradicted), and a docs-only merge is a *working* way to ship an accumulated tip rather than a useless one — which is most likely how `#556`'s `apps/web` changes actually reached production, since the next two deploys after it were these two docs merges. **(10) NOTHING WAS STRANDED, confirmed 2026-09-08 — the "recovery needs no re-merge" advice above held, and this is the first instance of it actually checked.** The founder reported that pushes across several chats had stopped going live, which was true during the window and had already resolved by the time he asked: `main`'s tip `0cabd27` (#551, the draggable UrgAns rail) was live, confirmed by **dragging the rail in production** rather than by any status read. So the accumulated tip shipped on the next successful deploy exactly as this bullet promises, with no re-merge and no dashboard action. **The lesson for the next report of this shape: check whether it is still true before doing anything.** A feature the tip introduced answered that in one gesture where four status reads could only infer — but **there is a purpose-built probe now and it is strictly better, so reach for it first:** `curl -s https://app.urganize.app/api/version` reports the deployed commit sha, and comparing it to `git rev-parse --short origin/main` settles the question in one line without needing a feature to eyeball. It shipped hours after this bullet was written, from a parallel session answering the same report — see *"Is live up to date?" is a curl now* below.

**Environments:** Production = `main` on both Vercel projects. Vercel preview deployments per PR. No dedicated staging.
