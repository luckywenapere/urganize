# The company scoreboard (2026-10-02, internal, no flag)

> Moved out of CLAUDE.md on 2026-10-22 (verbatim). "This file", "above", "below" and "the X section" in here refer to the old single CLAUDE.md: find the named section in docs/notes/README.md.

`/admin/scoreboard` works out the numbers from the strategy doc (`docs/strategy/company-strategy.md`, sections 2 and 7) from the database each time it loads: weekly active paying teams (the North Star), MRR, second-release rate, week 4 retention, active teams in the last 30 days, trial to paid and activation, plus a row per team and a "Copy for the team group" button that writes the Friday post as plain lines. Internal (the `/admin` precedent), so no flag, no migration and no changelog entry. Gated by `verifyAdmin` through its backing route, `GET /api/admin/scoreboard`. Nothing is stored.

**Where things live.** `lib/scoreboard.ts` holds every rule that decides a number, pure and tested; `lib/scoreboard-server.ts` only reads and shapes rows; `lib/scoreboard-format.ts` turns a board into words (kept apart so the page does not ship the counting rules); `components/admin/ScoreboardView.tsx` is display only, so the layout can be looked at with made-up numbers.

**Eight things worth knowing before editing this:**

1. **The definitions are the strategy doc's, and the doc wins.** Each constant in `lib/scoreboard.ts` names the line it implements. Change the doc first, then the code.
2. **Task edits were recorded nowhere until this change.** `tasks` has no editor column and `task_activity` only ever held comment events. The task update route (`app/api/tasks/[id]/route.ts`) now writes one `task_activity` row per update, with the actor and the fields changed. Safe because nothing has shown that table since the activity feed was removed 2026-07-23, and fire-and-forget so a lost row never fails an update. Activity from before 2026-10-02 therefore undercounts task edits; the page says so. UrgAns-driven completions go through `TaskService` instead and are not logged there, but each one already leaves an `urgans_action` billing event with the same actor.
3. **Activity is read from eighteen tables that record who did something and when** (`ACTIVITY_SOURCES` in `lib/scoreboard-server.ts`): task activity, comments, task files, manually created tasks, task outcomes, task notifications, release files, release chat, new releases, notes, UrgAns actions, chats and usage events, pitches, press kit saves, the team brief, pitch kit fields and work requests. `activity_logs` is deliberately absent: nothing writes it. A missing table is reported on the page and never blanks the board.
4. **"Active" is read from the person, not the team.** A member who does anything in Urganize counts as active for every team they belong to. That is the doc's own wording ("did something in Urganize") and saves a join per table.
5. **An invited teammate's own empty team is left out.** Every account gets a workspace, so without this every teammate would add a dead team to every number. Same rule the app's access resolver uses: a team counts unless its owner belongs to someone else's team and has no real release of their own.
6. **A release belongs to its ARTIST's team** (`releases.artist_id` then `artists.workspace_id`), falling back to the owner's workspace. Owner alone misfiles a release a teammate created under their own account, since `POST /api/releases` stamps the caller as owner.
7. **Paying team, MRR and the rest, as built.** A paying team has a current Manager or Label subscription (a legacy plan id counts, matching `resolveTeamTier`); Solo, comped, allowlisted, zero-amount and the retired card trial do not. MRR is `active` and `past_due` subscriptions in their period, yearly divided by 12, Solo included, `cancelled` left out because it will not charge again. A release goes live on its release date, or when its last activity is done (the `isRecapEligible` rule turned into a timestamp); a second release counts if it was started any time up to 90 days after the first went live, including before. Week 4 retention counts any member active in days 21 to 27 after the team was made, for cohorts whose fourth week is fully over. Trial to paid uses trials that ended in the last 90 days, with comped and allowlisted teams left out and a payment from before the trial not counted. Activation reuses `lib/activation.ts`'s 3-day window.
8. **Every read is paged.** PostgREST returns at most 1,000 rows, and a plain read silently stops there. Each read walks pages up to a cap (20,000 rows for each activity table) and a capped activity table marks the board as a floor, which the page and the Friday post both say.

**Referred signups (added 2026-10-02, after the referral work).** The doc's "Referred signups | Signups from a user's invite" is a tile, a line in the Friday post and a `referredSignups` figure on the board. It counts teams that came in through a referral link, kept apart by source: invited by another team (`user_referrals`, the referral credits table) and through a commission partner (`team_referrals`), each with the last 30 days, all time and how many pay today. A referred team is counted once per source and only if it is a team on the board (the empty shell every invited teammate is given is left out, like every other number). **If either table is missing or unreadable the figure is `null` and shows "Not tracked", never a zero**, because a half-read answer would show a zero for a source that is really "not tracked yet"; the Friday post says "Referred signups: not tracked yet". The scoreboard loader only READS those two tables; a structural test pins that it never writes them.

Full suite 5,790 passing; the only failure is `vercel-ignore-build.test.ts`, which needs shell tools this Windows machine lacks and fails the same way without these changes. `tsc` clean apart from the documented `confirmed-action.test.ts` errors, `next build` green with `/auth`, `/dashboard`, `/locked`, `/onboarding` and `/settings` still static. The layout was looked at through a throwaway page with made-up numbers (deleted), at desktop width and at 375px in dark mode with no sideways scrolling. **Not verified:** it has never read the production database, so no real number has been seen; the admin session needed to open it cannot be minted here.

**Weekly return rate by signup week (URG-267, 2026-10-14, v1.124.2).** Under the team "Week 4 retention" table, `/admin/scoreboard` shows a cohort table of PEOPLE: one row per signup week (the last 8 Monday-start weeks in Lagos time, WAT/UTC+1, the current week included, empty weeks kept as rows), the cohort size, then for weeks 1 to 4 after signup "returned/size · %" (e.g. "3/7 · 43%"; counts first because the numbers are small). Rules, decided once in `lib/admin-signup-return.ts` (pure, 14 tests in `lib/admin-signup-return.test.ts`; words in `lib/admin-signup-return-format.ts`): (1) the cohort is every account by `profiles.created_at`, invited teammates included; the list is `ScoreboardInput.users`, filled by `loadScoreboardInput` from the profiles it already reads (every workspace owner, which is every account), so nothing new is read and no migration was needed. (2) "Active" is the Scoreboard's own rule, the same `input.activity` from the eighteen `ACTIVITY_SOURCES` tables; opening the app without doing anything does not count (the wider `/admin/metrics` rule is NOT used, on purpose, so the Scoreboard keeps one definition). (3) Week N is measured from each person's own signup moment: week 1 = days 7 to 13, week 4 = days 28 to 34; the signup week is not a column. The team "Week 4 retention" uses days 21 to 27 (the doc's "fourth week"), which is week 3 here, and the page says so. (4) A cell stays blank until that week is over for everyone in the cohort (cohort end + (N+1) weeks). (5) A cohort whose week 1 began before 2026-10-02 is starred and the page notes that task edits were not recorded before then. (6) Our own accounts are dropped by `withoutInternalAccounts` like every other number. The route (`GET /api/admin/scoreboard`, still behind `verifyAdmin`) sends it as `signupReturn` beside `scoreboard`; `buildScoreboard` and the Friday post are unchanged. A version bump and ledger line were added because the task asked for them; the founder pulled the ledger line the same day (internal admin work gets no entry), so 1.124.2 is a retired gap in the ledger. **Not verified:** no admin session or browser here, so the rendered table and real numbers have not been looked at.
