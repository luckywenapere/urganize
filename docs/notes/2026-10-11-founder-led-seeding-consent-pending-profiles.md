# Founder-led seeding: consent-pending profiles (2026-10-11, no flag)

> Moved out of CLAUDE.md on 2026-10-22 (verbatim). "This file", "above", "below" and "the X section" in here refer to the old single CLAUDE.md: find the named section in docs/notes/README.md.

Lane B of the spec's "Seeding plan". The founder pastes up to 30 managers from the sales list at `/admin/seeding`; each becomes a **consent-pending profile** with a claim link and a copy-paste WhatsApp or email message. The manager opens the link, sees a profile built with them, edits it, picks whether they are open to work, and publishes it only if they want to. Migration `20261010170000_seeding.sql`, **applied by the founder, not by this session**. No feature flag (founder rule). The page and routes are admin only; the public side is `/welcome/[token]`.

**This LOOSENS the strategy doc's seeded-profile rule, by founder decision (spec Q1's default), and goes on the Monday review log.** The doc allows seeded, unclaimed profiles only when built from credits already on a released release's public credit link. These are built from what the founder typed from his own sales list, with the person's consent asked before anything is public. The safeguards that keep it honest are structural, not promises: the profile is an unclaimed, **private** `person_profiles` row (two existing constraints refuse any other visibility while unclaimed), it is never listed, never served at `/p/{slug}` and never featured until the person publishes from their own signed-in account, and "removed on request" is "tell Wena and he deletes it". Featured (another lane) still needs their published profile.

### Things worth knowing before editing this

1. **The seam with Relationships.** The link is a `person_claim_invites` row, the table Relationships built for claims and nothing used yet. Its `workspace_id` was NOT NULL because a team sends those, so the migration drops that (an operator invite has no team). The token is shown once and only its sha256 is stored. If the Relationships claim flow lands later, it should read the same table; `seeded_profiles` is separate and holds only the operator's side.
2. **"Invited" is a seeding state, not a profile status.** The spec says status `invited`; adding a third `person_profiles.status` would have widened a check constraint Relationships owns. The profile stays `unclaimed`. States (`invited`, `opened`, `published`) come from three dates on `seeded_profiles`, summarised in `lib/seeding.ts` for the weekly numbers (each stage is "at least this far"; "this week" is the last 7 days).
3. **Opening is recorded by the browser, never on render.** WhatsApp and other chat apps fetch a link's page on the server when the message is sent, and counting that as "opened" would tell the founder somebody read a message they have not seen. The server page and the GET route write nothing; the client posts to `/api/welcome/[token]/opened` once it has run, and crawlers do not run scripts. A guard test holds it.
4. **Publishing is theirs alone, in four places.** (a) `parseClaimBody` strips any `visibility` or `slug` from the body and only takes a listing choice from an explicit `publish: true` plus `publishTo` of `directory` or `public`; (b) the claim route needs a signed-in account (`getAuthenticatedUser`, deliberately not the paywalled gate, so somebody finishing sign up is never refused by billing); (c) publishing needs a name and one role; (d) the only server code that writes a visibility other than `private` is the claim patch. `lib/seeding-guard.test.ts` reads the sources to hold all of it.
5. **The link is single use through a conditional update** (`where used_at is null and revoked_at is null`), the row being the lock, and is handed back if saving the profile fails so they can try again. A "New link" ends any unused link first, so two never work at once. Somebody who already has a profile of their own is refused rather than merged (409).
6. **People Urganize already knows are not given a second profile.** Creation looks each email and phone up in `person_identifiers` first and reports "Already on Urganize" instead, so a claimed person is never sent "we made you a profile".
7. **Private notes stay private.** `seeded_profiles.notes` is the founder's and is never shown to the manager. The only text copied onto the profile is the separate `bio_starter`, written to be shown, which the manager edits. UrgAns does not draft profile bios yet (the draft action for it was not on main), so the manager gets a plain editor; the seam is the bio field on `WelcomeClaimClient`.
8. **Sign-up return.** A manager with no account sees the profile read-only and chooses Create account or Sign in. `lib/welcome-intent.ts` (sessionStorage, re-validated, read without clearing so the card trial cannot eat it) hands them back to the link after the onboarding wizard, through one additive field on `resolvePostSignupDestination`. The wizard still makes them a team and a first rollout on the way, which is heavy for somebody who only came for a profile; a lighter sign-up for this path is a founder call, not built.
9. **The tables are RLS-on with no policies**, and `seeded_profiles` is touched by only `lib/seeding-server.ts` and the link route (a structural test).

**Not built:** automatic sending (the founder sends the message by hand; nothing is emailed from Urganize), the UrgAns bio draft, a weekly digest email, removing a seeded person from the admin page (delete the profile in the database for now), and a lighter sign-up.

### Verified

New tests: `lib/seeding.test.ts` (pure rules and copy), `lib/seeding-server.test.ts` (the real server code against an in-memory stand-in that enforces the migration's unique and profile rules) and `lib/seeding-guard.test.ts` (the structural rules). **Nine deliberate breaks, each caught by a named test and restored:** creating a profile as public, treating any truthy `publish` as a yes, dropping the single-use condition, recording an open on render, removing the admin check from a route, allowing a second profile for somebody who has one, allowing a row with no contact, ignoring "already on Urganize", and miscounting published rows as not opened.

**Not verified against a real database or a real session.** No profile has been created, no link opened or claimed, no message sent, and the migration is unapplied from here.

### Activation

1. Apply `20261010170000_seeding.sql`.
2. Merge. Nothing to switch on.
3. Open `/admin/seeding`, paste two people (your own second email first), create, copy the link, open it in a private window, check it reads as intended, create an account or sign in, publish, and confirm `/p/{slug}` and the directory only show them after that, and the admin page moves them to Published.
