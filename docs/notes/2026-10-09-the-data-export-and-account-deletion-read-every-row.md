# The data export and account deletion read every row (2026-10-09, v1.92.10, no flag)

> Moved out of CLAUDE.md on 2026-10-22 (verbatim). "This file", "above", "below" and "the X section" in here refer to the old single CLAUDE.md: find the named section in docs/notes/README.md.

Found by tracing what else the 1,000-row cap in v1.92.9 could reach. Two places where completeness is the whole point were reading with one unpaged `select`, and one place was reading other teams' rows.

1. **The account data export dropped rows without saying so.** `readSection` in `app/api/account/export/route.ts` did one `select('*').in(column, values)`. PostgREST stops a response at 1,000 rows, so a team with 1,024 activities got 1,000 in the JSON and the spreadsheet, and the section read as complete because the export's own `truncated` flag only trips at `EXPORT_ROW_CAP` (50,000). It also sent every task id in one `.in('task_id', ...)` to read comments and outcomes: a URL of about 38 KB, which the gateway refuses, so those two sections read as "unavailable" for any big team. It now reads through `readInChunks` (`lib/paged-rows.ts`): ids in chunks of 150 (`IN_LIST_CHUNK`), each chunk a page at a time, up to `EXPORT_ROW_CAP + 1` rows so `buildSection` can tell a list that hit its cap from one that ended there.
   - **Each read is ordered by a unique column** so a page boundary never skips or repeats a row: `id` by default. `release_payback` (primary key `release_id`) and `user_presence_days` (primary key `user_id, day`) have no `id`, so they carry `orderBy` explicitly; a test pins both. Add the same to any new section whose table has no `id`.
   - A failed page still reads as `unavailable` with the message, never as an empty section. The export stays an open route (no paywall), untouched.
2. **Account deletion left attachment files behind.** `removeUserStorageObjects` in `app/api/account/delete-now/route.ts` lists every storage object before the database rows (which cascade) go. Its five reads were single selects, so a user with more than 1,000 assets, or whose rollouts held more than 1,000 activities, had the rest skipped, and the one `.in('task_id', taskIds)` was too long to send. Each list is paged now and the id lookups are chunked, with a read that fails still logged and skipped so deleting an account is never blocked. Task attachments are switched off in production, so the files at risk today are mostly assets, but the rule is the same.
3. **Home read every team's shows.** `loadVisibleShows` in `lib/home-server.ts` selected the first 100 shows in the 30-day window across ALL teams, then filtered by access in memory, so once other teams held 100 shows between them a team's own next show and its waiting DJ links fell off Home. It is scoped by owner in the query now (`GET /api/events` and the pitches read already were), keeping the in-memory access check on top. `lib/home-tenant-scope-guard.test.ts` holds both reads.

**Verified:** new tests for `readInChunks` (chunk size, past 1,000 rows, the ceiling, a failed read, exactly reaching the ceiling), the export and deletion wiring and the Home scope; the guards fail with the page range removed, the `+ 1` removed, the task-id chunking removed, the orderBy overrides reverted, and the owner scope removed from Home. One mutation (`>=` against `>` at the ceiling) first survived and now has its own test. **Not verified against a real database:** no team over 1,000 activities has been exported for real, and no account with many files has been deleted. Worth one pass on the team that triggered the earlier fix: download the data export and compare the activity count with the Catalogue's.
