# The delete-rollout dialog asks the server how many activities go with it (2026-10-09, v1.92.2, no flag)

> Moved out of CLAUDE.md on 2026-10-22 (verbatim). "This file", "above", "below" and "the X section" in here refer to the old single CLAUDE.md: find the named section in docs/notes/README.md.

Found on the live app: the first time Settings → Delete rollouts opened `DeleteReleaseDialog` on a rollout with 32 activities, it said "This permanently deletes the rollout and all attached files", the wording reserved for an empty rollout. The count was a prop the caller computed from the client task store (`tasks.filter(t => t.releaseId === id).length`), and that store can be empty (Settings is often the first route a session hydrates, and the dialog can open before `loadCommandCenter` lands), a stale cached copy (`COMMAND_CENTER_CACHE_KEY`), or truncated (`getTasksForUser` is capped at `TASK_LIST_MAX_ROWS` across the whole workspace). Any of those read as 0, and 0 dropped the activities from the sentence.

- **The dialog owns the count now; the prop is gone.** `DeleteReleaseDialog` takes no `tasksTotal`. Each time it opens on a rollout it calls `fetchReleaseTaskCount` (`lib/delete-release-task-count.ts`), which reads `retention.taskCount` from the existing `GET /api/releases/[releaseId]` (an exact, head-only `count` on `tasks.release_id`, the same set the DELETE cascades). No new route, no schema change. Both mounts (Settings' `ReleasesSection` and the workspace's test-rollout exit in `WorkspaceView`) dropped their client-store counts.
- **Three states, and only a known zero may leave activities out.** `loading` and `unknown` both say "…the rollout, all of its activities, and all attached files", with a small "Counting its activities…" / "We couldn't count its activities right now." line under it. A known number says "its N activities" (the dialog said "tasks" before; the product's word is "activities", and the Settings tooltip beside it already said so).
- **Never blocks deletion for long.** The Delete button waits only while the count is loading; `fetchReleaseTaskCount` aborts and returns `unknown` after `TASK_COUNT_TIMEOUT_MS` (8s), and every failure (no session, non-2xx, a body without the count, a network error) is `unknown`, never 0. Delete is enabled in the `unknown` state.
- **Settings rows show when each rollout was made** (`formatRolloutCreatedLabel`, `lib/settings-rollout-row.ts`, date and time in the viewer's locale), so identical "Untitled rollout" rows can be told apart. A count was deliberately NOT added to the rows: it would come from the same client store this fix stops trusting.
- **Tests:** `lib/delete-release-task-count.test.ts` (parsing; the request; known zero only from a server zero; unknown on 500/403/bad body/network error/no token; the timeout aborts and resolves unknown under fake timers; the copy for each state; a source scan that the dialog fetches, takes no count prop and never reads the task store, that no `<DeleteReleaseDialog` mount passes a count, and that the GET still answers an exact head-only `retention.taskCount`). `lib/settings-rollout-row.test.ts`. Mutation: restoring `main`'s dialog and `ReleasesSection` fails three of the scan tests.
- **Not verified in a browser or against a real database.** Preview pass: hard-refresh straight onto Settings → Delete rollouts, tap Delete on a rollout with activities and confirm the dialog shows "Counting its activities…" with Delete held, then "its N activities"; tap Delete on a fresh empty rollout and confirm the zero wording; with the network throttled to offline after the page loads, confirm the "couldn't count" wording appears and Delete still works once back online. Also the test-rollout banner's "Delete test release" (flag `NEXT_PUBLIC_FEATURE_TEST_RELEASE`).
