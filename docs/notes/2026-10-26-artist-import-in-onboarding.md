# Artist import in onboarding (2026-10-26, v1.184.0, NEXT_PUBLIC_FEATURE_ARTIST_IMPORT ships on)

Founder approved the mock ("alright build"). A new onboarding step, right after "What are you working on?" and before the account: type an artist's name, pick the profile, watch their releases arrive, then "Add another artist?". Skippable at every point.

## How it works

- **Order**: persona, working on, **artist import (step id 11)**, falls apart, ..., opt-in, account, paywall, welcome, invite. The id is stable and not a position; `isPostAccountStep` and `lastQuestionStep` in `lib/onboarding-steps.ts` now name the post-account steps explicitly, because id 11 is greater than the account id and the old `step > account` rule would have called it post-account. Held by `lib/artist-import/onboarding-steps.test.ts`.
- **Sources** (`lib/artist-import/providers.ts`, pure parsers; `fetch.ts`, the calls): Deezer first (no key, has release type, cover and fan count), Apple iTunes lookup when Deezer finds nothing. Spotify is NOT used: new-app approval limits could block us at launch. Measured 2026-10-26: both return real data (Burna Boy: 82 releases on Deezer).
- **Public lookups before the account**: `GET /api/artist-import/search?q=` and `GET /api/artist-import/releases?provider=&id=`. Open on purpose, a per-address in-memory limit (`rate-limit.ts`, 40 a minute, best effort per server instance), cached an hour. Source ids are digits only (`isSafeSourceId`).
- **Held until the account exists**: the picked artists (provider, id, name, count) sit in localStorage `urganize.onboarding.artist-imports` (`pending.ts`). NOT in the onboarding draft: that also rides in the email-confirmation metadata. A confirmation link opened on another device loses them; the person adds the artist from its page later.
- **Saved at the hand-off**: `runPostSignupHandoff` calls `saveImportedArtists` before the rollout is made, so the rollout's artist lookup finds the same artist. `POST /api/artist-import` takes only `{provider, id, name}` and pulls the releases AGAIN on the server; the browser never sends a list of releases to store. Best effort and bounded (12 s): a failure never strands the sign-up.
- **Where they live**: new table `artist_catalogue_releases` (migration `20261026150000`, applied to live 2026-10-26, RLS select for team members, writes service-role only, upsert on `(artist_id, source, source_id)`). **Not `releases`**: rollout counts, plan limits, the Home "plan a rollout" card and the scoreboard all count `releases`, and 80 past singles would make each of them lie. Shown on the artist page in `ArtistCatalogueCard` (renders nothing when empty). Read by `GET /api/workspace/artists/[artistId]/catalogue`.
- **Artist limit**: `importArtistCatalogue` uses `checkArtistAllowance`; over the limit it saves nothing for that artist.
- **Last screen** ("last released X months ago, plan the next one?") shows only for "Nothing planned yet" and only when release dates exist. "Plan the next release" turns the answer into a single for that artist and moves on; the step list then grows by the rollout steps.
- Kill switch: `NEXT_PUBLIC_FEATURE_ARTIST_IMPORT=false` removes the step. Analytics: `onboarding_artist_import_viewed`, `_picked`, `_imported`, `_import_skipped`, `_plan_next`.

## Traps

- Covers are remote URLs (Deezer, Apple), never copied. The step and the card use plain `<img>`, not `next/image`.
- `components/` must not contain the word "workspace" (house-copy ratchet): the catalogue fetch lives in `lib/artist-import/client.ts`.
- Not verified here: the post-account save (`saveImportedArtists`, `POST /api/artist-import`) was type-checked and reasoned through but not run end to end, because a test sign-up on this machine writes to the live database. Manual pass: sign up with an artist picked, check the artist page's Catalogue card and that the roster has one artist, not two.
- A Deezer outage at search time falls back to Apple for that search; the edge cache keeps that answer for an hour.
- 19 unrelated guard tests in `pnpm test` fail on this Windows checkout (CRLF reads in file-scanning tests); they failed before this change.

## Existing accounts (v1.187.0, founder approved mock "import-releases-existing")

- **Import releases** button: Artists page (a quiet button beside the + on the phone header; under the list on desktop, because `section-content-top-guard` keeps anything out from between the tab row and the list) and the Catalogue card on each artist's page, which now always draws and prefills the artist's name.
- `components/artists/ImportReleasesDialog.tsx` (dialog plus `ImportReleasesButton`, which owns its open state): search, pull, done, add another. It saves at once through `saveArtistImport` (`lib/artist-import/client.ts`, POST `/api/artist-import`); an artist already on the roster by name gets the releases, no duplicate. The covers come from the public lookup, the save pulls again on the server.
- After a save it dispatches `CATALOGUE_CHANGED_EVENT` (the Catalogue card refetches) and force-loads the roster store.
- Shared bits (`Cover`, `formatFans`, `kindLabel`, `initials`) moved to `components/artists/ImportParts.tsx`; the onboarding step uses them too.
- Tested 2026-10-26 with a throwaway account: Wizkid imported (78), a second import said "already up to date", the card showed 78 covers; account, data and invite deleted afterwards.

## Codes and Get link (v1.189.0, founder approved mock "get-link-catalogue")

- **Codes**: `artist_catalogue_releases` gained `upc`, `isrc`, `codes_checked_at` (migration `20261026180000`, applied to live 2026-10-26). Deezer gives the UPC on `/album/{id}` and, for a single, the ISRC on `/track/{id}` (two calls); an EP or album takes the UPC only (enough for a link). Apple gives neither, so Apple rows are stamped checked at import. `enrichCatalogueCodes` (`lib/artist-import/links-server.ts`) runs after the import reply and again from every catalogue read that finds unchecked Deezer rows: batches of 25, newest first, 150 ms apart (Deezer allows about 50 calls in 5 s), rows claimed by stamping `codes_checked_at` first, put back when Deezer cannot be reached. Measured with a test account: Wizkid, 78 of 78 UPCs and 68 ISRCs, all filled within about 15 s of opening the page.
- **Get link** (`makeCatalogueLink`): one Altlink link per catalogue release, in its own table `catalogue_smart_links` (unique on `catalogue_release_id`), NOT `release_smart_links` (that one is keyed to a rollout). Order: ownership, existing link, a code, Altlink on, the daily cap, a claim row, then Altlink. `external_release_id` is `catalogue:<row id>`. A second tap returns the same link; a fresh `pending` claim answers busy.
- **The notice** is shown before every link (`LinkNotice` in `ArtistCatalogueCard.tsx`): public link, made by Altlink so we cannot edit or delete it, uses 1 of today's links, N left.
- **The daily cap**: counted from `catalogue_smart_links` (links `made` today in Lagos, plus claims in flight), per team. The limit is `app_settings` key `catalogue_links_per_day`, value `{"limit": N}`, default 10 (`lib/artist-import/codes.ts`). **Raise it with no deploy** by upserting that row. Failed and rate-limited attempts do not count. **The 10 is a guess**: Altlink publishes no limits (checked 2026-10-26: our code and notes, its health endpoint headers, its public site). The pilot runs 21 Oct 2026 to about 19 Jan 2027. Questions to send Altlink: links per day and in total, request rate limit and its error, a cap per creator email, whether links can be edited or deleted, what happens to links when the pilot ends. Update this paragraph and the setting when they answer.
- **No code**: the row shows "Add code" (`PATCH .../catalogue/[releaseId]/codes`, a UPC or an ISRC, told apart by shape) instead of Get link.
- **Tested** with a throwaway account on localhost against the live database and a deliberately invalid Altlink key (so no real link was made): the notice, the failed path (error shown, count stays 0), the cap notice (setting read from the database), add-code validation, another team's release refused. **Not tested**: a real link made through Altlink, because that creates a real public link in the partner pilot. Do one by hand and check the row reads "made" and the URL opens.
