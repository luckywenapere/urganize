# Push sends and checkout starts have time limits (2026-10-09, v1.92.11, no flag)

> Moved out of CLAUDE.md on 2026-10-22 (verbatim). "This file", "above", "below" and "the X section" in here refer to the old single CLAUDE.md: find the named section in docs/notes/README.md.

Found by reading, not by a report: three kinds of call to outside services had no time limit, so a service that accepted the connection and then went quiet held the caller open for as long as the platform allowed. **No flag, no migration.**

1. **Pushes.** Neither transport had a timeout. Web push (`lib/push-server.ts`) now passes `timeout: PUSH_SEND_TIMEOUT_MS` (8 seconds) to `web-push`; every FCM request (`lib/fcm-server.ts`, the token exchange and each send) carries `AbortSignal.timeout(PUSH_SEND_TIMEOUT_MS)`. This matters twice: a task assignment awaits its push inside the request that made it, so one slow endpoint left a teammate's save hanging, and the morning cron flushed pushes before the email outbox in one 60 second function.
2. **The morning cron's minute.** `lib/push-limits.ts` holds the sums (pure, tested): the cron plans to use 50 of its 60 seconds, the push flush gets 15, and `emailBudgetMs(elapsed)` gives the email drain what is left, never more than 40 seconds, never negative, minus 10 seconds of slack because the drain only checks its budget between sends and one send can abort as late as 10 seconds in (`lib/email/transport.ts`). A clock reading that is not a number counts as time already spent, never as free time. **Before this, the onboarding sequence's days 2 to 7 (which ride that cron) could be starved by one stuck push.**
3. **`flushDueNotifications` stops on a clock and sends five at a time.** It reads the same due rows, then works in groups of 5 (`FLUSH_CONCURRENCY`), checking the budget before each group and leaving the rest unclaimed and due, so the login ping or tomorrow's cron picks them up. Each row is still claimed before it is sent. One send that throws no longer loses the counts of the rest (it is caught per row). The default budget is `PUSH_FLUSH_BUDGET_MS`, so the login ping's call (limit 20) is bounded too.
4. **Starting a checkout.** `lib/paystack-init.ts` (`fetchPaystackInit`) is the one way the three routes that start a Paystack checkout (`billing/start-checkout`, `billing/change-plan`, the retired `trial/start-checkout`) call Paystack. It gives up after 15 seconds and turns a timeout or a network failure into an ordinary failed 504 with a plain message, so each route's existing "not ok" branch runs: it drops the pending `payments` row and tells the customer to try again. It uses a controller and a timer (not `AbortSignal.timeout`) so the wait is cleared when Paystack answers and the timeout can be tested with fake timers.
5. **The money-changing Paystack calls were deliberately NOT given this.** A refund and the creation of a delayed subscription (`webhooks/paystack`, `billing/cancel-trial`) are not safe to abort: an abort after Paystack has already acted leaves the outcome unknown, and treating that as a failure could double-charge. A guard test asserts neither file uses the helper. Starting a checkout is safe to give up on: nothing is charged until the customer finishes on Paystack's own page, and a retry uses a fresh reference.

**Tests:** `lib/push-limits.test.ts`, `lib/engagement-flush.test.ts` (the real flush against an in-memory stand-in for the two queries it makes, with fake timers), `lib/push-timeout-guard.test.ts` (source scans of both transports, the cron and the flush), `lib/paystack-init.test.ts`. **Sixteen deliberate breaks, each confirmed applied and each killed by a named test** (timeout removed from web push and from one FCM request, the flush budget dropped from the cron, the drain given a flat 40 seconds, the budget check removed, concurrency raised, the per-row catch removed, the slack removed, the negative clamp removed, a bad clock reading treated as zero, the abort never firing, the timer not cleared, a timeout rethrown, the status turned to 200, a route back on a bare fetch, a route no longer dropping its pending row).

**Not verified:** nothing has run against a real push service, Resend or Paystack, and no cron has run with this code. The 8, 15 and 50 second figures are reasoned from the 60 second function limit and the 10 second email send abort, not measured. Not checked for any other service: the Paystack calls inside `lib/paystack-server.ts`, `lib/linear-server.ts`, the transcription route and the genre-prediction proxy already carry timeouts.
