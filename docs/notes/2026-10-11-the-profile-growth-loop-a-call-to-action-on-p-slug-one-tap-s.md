# The profile growth loop: a call to action on /p/{slug}, one-tap share, funnel events (2026-10-11, v1.114.0, no flag)

> Moved out of CLAUDE.md on 2026-10-22 (verbatim). "This file", "above", "below" and "the X section" in here refer to the old single CLAUDE.md: find the named section in docs/notes/README.md.

The best growth loop is credits, then a claim, then a public page at `/p/{slug}` the person shares to get work. Two gaps closed: the page ended in a plain "Delivered with Urganize" line, and nothing in the loop was measured. No feature flag (the page change is copy and two links; the share buttons only show to the page's owner). One migration, safe in either order.

1. **The foot of every person page** (claimed and unclaimed) is `components/people/ProfileGrowthFooter.tsx`: the "Made with Urganize" mark /pitch and /k carry, then "Work in music? Get your own page" and "Manage artists? Run your rollouts on Urganize". **Server component, plain `<a>` links, no script**, same `.kit-island` palette. Each goes to `GET /api/public-profile/cta?slug=&cta=collaborator|manager`, which counts the tap and 303s to `/onboarding?from=profile&slug=&cta=`. A bad value still lands on sign-up, without attribution.
2. **`?from=`, never `?ref=`.** `?ref=` is a partner referral code (`lib/referral-intent.ts`) and "PROFILE" is a valid code shape, so `?ref=profile` would be posted to `/api/referrals/attach`. A guard holds it.
3. **Sign-up attribution** (`lib/signup-source-intent.ts`): onboarding remembers `from/slug/cta` on arrival (localStorage, 30 days, last link wins, its own key beside the referral one); the claim page's "Sign up to claim" marks `claim`. At the end of onboarding, `finishToDashboard` posts it once to `POST /api/signup-source` (open route), alongside the referral report. The route records `signup_from_profile` only for an account made in the last 7 days, once per account (unique index), and sends a slug only for a claimed, public page. **There was no signup event before this:** `signup_completed` is declared in `lib/analytics/shared.ts` and fired nowhere, so `signup_from_profile` is its own event rather than a property on one.
4. **One-tap share** (`components/people/ShareProfileLink.tsx`: Copy link, the phone's share sheet where there is one, Send on WhatsApp). On the claim's last step ("Your page is saved.") it now comes first, above "Start a rollout", and only for a page they chose to show. On `/p/{slug}`, `OwnProfileShare` shows it to the owner: sessions live in the browser, not a cookie, so the server cannot know the reader; after the page draws, a signed-in reader's browser asks `/api/claim-profile` for its OWN profile and shows the row only when that slug is this page's. Strangers cost no request, and no user id is put in the HTML.
5. **Funnel events**, all built from allowlists in `lib/profile-growth.ts` (no names, contacts or release titles; a slug only for a page its owner published, never for an unclaimed one). Server-side through `lib/profile-growth-server.ts`, always via `afterResponse`: `credit_submitted` (anonymous, `$process_person_profile: false`), `claim_completed`, `profile_published` (only on the move from not shown to shown), `public_profile_viewed` (from the `/p` render, anonymous), `public_profile_cta_clicked` (the redirect route), `signup_from_profile`. Browser-side because a chat app fetches a pasted link on the server before anyone reads it (the seeding page's rule): `credit_link_opened`, `claim_page_viewed`, `profile_link_shared`. **`public_profile_viewed` is server-side as asked, which breaks the KitViewBeacon precedent;** link previews, crawlers, scripts and prefetches are filtered by `isLikelyBot` / `isPrefetchRequest`. The older browser `profile_viewed` (directory funnel) still fires beside it; do not add the two.
6. **Migration `20261011150000_profile_growth_events.sql`**: one table (`kind` profile_view | cta_click | signup, `person_id`, `cta`, `source`, `user_id` on signup rows only), RLS on with no policies, written only by `lib/profile-growth-server.ts` (a guard holds it). No IP, user agent or slug. Before it is applied the inserts fail, are logged and ignored.
7. **`/admin/profile-funnel`** (Numbers group, ADMIN_EMAILS): credits submitted, unclaimed profiles made, claim emails sent (`person_claim_invites` channel email by `sent_at`, with links shared by hand beside it), claimed, published, views, CTA taps, sign-ups, last 30 days. **Not a cohort**: each step counts its own window, so a step can be bigger than the one before; the page says so and the ratio reads "x% of" below 100% and "N times" above. Our accounts are left out with `internalAccountEmails` (credits on our rollouts, profiles our teams made, invites we sent, claims, views and taps on our pages, our sign-ups). The three steps from the new table read "Not tracked" until it exists. Pure rules in `lib/admin-profile-funnel.ts`.

**Not touched on purpose:** claim email sending (`app/api/releases/[releaseId]/credit-claims`, `lib/claim-sweep*`, email modules), which another branch is instrumenting with `claim_email_sent` / `claim_reminder_sent`. **Known gaps:** the collaborator CTA lands on the normal onboarding, which still makes a team and a first rollout (the seeding section's "lighter sign-up" founder call); `profile_published` fires from the claim flow only, not from the Settings profile editor or `/welcome/[token]`; views count the owner looking at their own page.

**Tests:** `lib/profile-growth.test.ts` (parsers, attribution, bot filter, payload allowlists, the copy bar), `lib/signup-source-intent.test.ts`, `lib/admin-profile-funnel.test.ts`, `lib/profile-growth-guard.test.ts` (structural: no-JS footer, sessionless redirect, browser-only beacons on previewed pages, afterResponse everywhere, one writer for the table, read-only admin route, `?from=` not `?ref=`). **Not verified in a browser or against a real database:** the footer at 375px, the share sheet on a phone, the owner check, and the PostHog events arriving.

**Activation:** apply `20261011150000_profile_growth_events.sql`; merge; open a public `/p/{slug}` from a phone in a private window, tap each link and confirm the onboarding address carries `from=profile`; claim a test page and use Copy link; check `/admin/profile-funnel` and PostHog Live events.
