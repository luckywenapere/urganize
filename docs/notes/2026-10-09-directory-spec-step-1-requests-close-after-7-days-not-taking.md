# Directory spec, step 1: requests close after 7 days, "Not taking work", reply rate (2026-10-09)

> Moved out of CLAUDE.md on 2026-10-22 (verbatim). "This file", "above", "below" and "the X section" in here refer to the old single CLAUDE.md: find the named section in docs/notes/README.md.

From `Urganize_Profiles_and_Directory_Spec.docx` (Oct 9, 2026), step 1: three fixes to the live directory request flow, no new screens. Not a scope expansion. Migration `20261009130000_work_requests_expired.sql`, **not applied until the founder applies it**; the code works either way (see 1).

1. **A request nobody answers in 7 days closes.** `status` gains `'expired'`, so `work_requests_status_check` is widened (the only other thing the migration adds is an index on waiting rows). **Read-time first, so it is right before the migration lands:** `effectiveRequestStatus` / `withEffectiveStatus` in `lib/work-requests.ts` read a waiting request older than `WORK_REQUEST_EXPIRY_DAYS` as `expired`, and every route does the same, so a missed cron day costs a slot and nothing else. `canAnswerWorkRequest` takes `createdAt` and refuses a late answer; the answer route also carries `.gte('created_at', workRequestCutoff())` on its conditional update, so the refusal does not rest on one check (409 "This request closed after 7 days with no answer."). The open-request cap does not count stale requests. `POST /requests` closes a stale request to the SAME person and role before inserting, because the partial unique index `work_requests_open_key` would otherwise refuse "ask again" until the sweep ran. The write is `runWorkRequestExpirySweep` (`lib/work-request-expiry-server.ts`), another passenger on `/api/cron/due-date-notifications` (two cron slots, Hobby plan), never throws and is not behind the directory flag. An unreadable date is never stale (closing somebody's ask on a guess is the wrong way to be wrong).
2. **"Not taking work" is enforced, not just shown.** `canReceiveRequests` (anything but `closed`, fail open) gates `POST /requests` (409 "<name> is not taking work right now.") and hides the Ask button on the directory card. The profile stays visible: spec open question 2, answered as proposed, because a manager who is full can still be found and respected.
3. **`/admin/directory` shows how requests are doing.** `summarizeWorkRequests` reads `work_requests` for the last 90 days: sent, said yes, said no, closed with no answer, waiting, a weekly table (Monday UTC, newest first) and a **reply rate that leaves out requests still waiting** (a request sent an hour ago has not had its chance), `null` ("Not enough yet") when there is nothing to divide. This is spec test 4's "messages get a reply 40% of the time". A table that cannot be read is reported by name, like the other three.
4. **Wording:** the sender sees "No answer in 7 days, so this one closed. You can ask again." and the recipient "You did not answer in 7 days, so this one closed."
5. **Guards:** `lib/work-requests-wiring-guard.test.ts` reads the real route sources (comments stripped) and fails if a handler stops going through the rules; `lib/directory-schema-guard.test.ts` holds the status list in step with the CHECK. Nine deliberate breaks (stale boundary inclusive, closed availability allowed, non-waiting rows stale, expiry days changed, waiting in the reply denominator, expired read as waiting, the cap counting stale rows, the answer update ignoring the cutoff, the sweep touching non-waiting rows) were each caught by a named test.
6. **Not verified:** nothing has run against a real database or a real session. No request has closed for real, the sweep has never run, the migration is unapplied, and `/admin/directory` has not rendered with real data.
